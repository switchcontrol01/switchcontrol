TASK

Implement a safe premium tweak revert system with ownership tracking, including premium power plan actions.

PROBLEM

Currently the app cannot distinguish between:

- tweaks applied by the app
- tweaks that already existed before the app

This creates a major safety issue:
when a trial expires, reverting premium tweaks may undo the user’s original system configuration.

This same problem also applies to power plans:
if the app changes the active power plan during trial or premium use, it must not destroy the user’s original power plan setup when premium ends.

That is unacceptable.

GOAL

Only revert tweaks and power plan actions that were explicitly applied by the app during trial or premium usage.

Never revert pre-existing system configurations.
Never blindly overwrite manual user changes.
Never report success unless revert is verified.

IMPLEMENTATION

1. Add ownership tracking for every tweak

When a tweak is applied by the app, store a metadata record such as:

appliedTweaks[tweakId] = {
appliedByApp: true,
timestamp: Date.now(),
previousState: exactVerifiedStateBeforeApply,
appliedState: exactVerifiedStateAfterApply,
revertFailed: false,
conflictDetected: false
}

Important:
previousState must store the exact verified system state required to restore the tweak safely, not just a boolean.

Examples:

- registry value + whether it existed
- service startup type
- service running state if relevant
- adapter property value
- policy existence or absence
- multi-field state for complex tweaks

2. Add a first-run baseline scan

On first launch only:

- detect all tweak states
- create ownership records for already-active tweaks as:

appliedByApp: false

This marks them as user/system-owned and protected from app-driven revert.

Also store:

baselineInitialized: true

This baseline scan must run only once per device/profile unless explicitly reset by the user.
Do not overwrite ownership records on normal startup.

3. Add separate ownership tracking for power plan actions

When the app changes the active power plan, store a separate record such as:

powerPlanOwnership = {
appliedByApp: true,
timestamp: Date.now(),
previousPlanGuid: exactPreviousPlanGuid,
previousPlanName: exactPreviousPlanName,
appliedPlanGuid: exactAppliedPlanGuid,
appliedPlanName: exactAppliedPlanName,
revertFailed: false,
conflictDetected: false
}

Important:

- power plan tracking must be separate from generic tweak tracking
- restore the exact previous active plan, not a guessed default like Balanced
- if the user already had a custom plan active before the app changed anything, that exact plan must be restored

4. Update revert logic for expired trial / premium removal

On trial expiration:

- collect premium tweaks
- collect premium network tweaks
- check power plan ownership if the active power plan was changed by a premium flow
- only consider items where appliedByApp === true
- restore previousState / previous plan
- verify the revert actually succeeded
- only clear ownership metadata after successful verification

Do NOT touch any tweak or power plan where appliedByApp === false

5. Detect manual user changes before revert

Before reverting an app-owned tweak:

- compare current live state with the stored appliedState

If the live state no longer matches what the app originally applied, do not blindly overwrite it.
Mark:

conflictDetected: true

and skip automatic revert for that tweak.

Do the same for power plan:

- compare current active plan against appliedPlanGuid
- if the user manually changed the power plan after the app applied one, do not force a revert
- mark conflictDetected: true and surface it in UI

This prevents overwriting manual changes made outside the app.

6. Handle partial failures safely

If revert fails for any tweak or power plan:

- keep the ownership record
- set revertFailed: true
- do not pretend the revert worked
- surface the failure in UI
- allow retry later

Do not delete tracking data until revert is verified.

7. Apply this exact ownership system to:

- premium tweaks
- premium network tweaks
- premium power plan actions

Use separate namespaces or grouped storage so system tweaks, network tweaks, and power plan ownership remain clean and auditable.
