TASK
Implement the full professional auto-update system for SwitchControl using Electron’s real installed-app updater flow.

GOAL
When a new SwitchControl version is released, installed Windows users must automatically detect it inside the app, download it in the background, and be prompted to restart and install. This must feel like a premium desktop product, not a website download hack.

STACK
Use:
- electron-builder
- electron-updater
- NSIS Windows target
- hosted private update source
- CI publishing flow

DO NOT
- do NOT build a fake frontend-only version checker
- do NOT make the website download page the main update path
- do NOT mix update state with premium/license state
- do NOT make the renderer own update logic
- do NOT ship a temporary solution as the final architecture

ARCHITECTURE
Main process owns the updater.
Renderer only consumes updater state via preload IPC.
Release artifacts + metadata are published from CI.
Installed app checks update source and handles update lifecycle.

IMPLEMENTATION

1. MAIN PROCESS UPDATER SERVICE
Create a dedicated updater module in Electron main process using electron-updater.
Implement:
- initUpdater()
- checkForUpdates()
- downloadUpdate()
- quitAndInstall()
- getUpdaterState()

Wire these events:
- checking-for-update
- update-available
- update-not-available
- download-progress
- update-downloaded
- error

Store a clear in-memory updater state object:
- status
- currentVersion
- availableVersion
- downloadPercent
- bytesPerSecond
- transferred
- total
- releaseNotes
- releaseDate
- errorMessage
- checkedAt

2. PRELOAD
Expose a safe typed API:
- app.getVersion()
- updater.getState()
- updater.check()
- updater.download()
- updater.quitAndInstall()
- updater.onEvent(callback)

3. RENDERER UI
Add a premium update experience:
- Settings page update card
- startup banner if an update exists
- background download progress bar
- “Restart to update” CTA when ready
- release notes block
- “You’re up to date” state
- “Checking…” state
- error state with retry

4. STARTUP BEHAVIOR
On app launch:
- initialize updater
- do a silent check after app is stable
- do NOT annoy users if nothing is available
- if update exists, show subtle premium banner
- if update is downloaded, surface restart CTA clearly

5. MANUAL CHECK
Add “Check for updates” in Settings.
This must call the real main-process updater, not compare strings in the frontend.

6. PUBLISH CONFIG
Configure electron-builder publish settings for a private hosted release source.
Make sure update metadata is generated and published with releases.
Use NSIS Windows target.

7. CI RELEASE FLOW
Create/finish release pipeline so that on release:
- app version is bumped
- installer is built
- latest update metadata is generated
- artifacts + metadata are uploaded to the configured update host
- release notes are attached
- logs clearly show publish success/failure

8. VERSIONING
Use semver only.
No custom loose version parsing.

9. UPDATE CHANNELS
Implement update channel support cleanly:
- stable now
- beta-ready structure for later

10. LOGGING
Add clean logs in main process:
- updater initialized
- checking
- available / not available
- download progress
- downloaded
- install trigger
- errors

11. SAFETY
If update server is unreachable:
- app must not crash
- renderer must show graceful retry state
- normal app use must continue

12. DESIGN REQUIREMENTS
The update UX must feel expensive and intentional:
- premium glass card styling
- subtle glow accents
- fluid motion
- not bloated
- no ugly stock system feel
- no spammy modal stack

HOW A NEW RELEASE SHOULD TRIGGER FOR EVERYONE
Implement and document this exact release path:
1. Developer bumps app version
2. CI builds installer + update metadata
3. CI uploads artifacts to update host
4. Installed apps check update source on startup or manual check
5. If newer version exists, users get in-app update prompt
6. Users download and restart to install

This trigger must be automatic once the new release is published correctly.
