Release-critical NIC + Network Tweaks audit.

I reviewed "nic-executor.js". It is improved, but it is still not robust enough for cross-machine production use.

Confirmed problems in the current NIC executor:

1. Verification logic is too strict and can falsely fail
   Current code verifies with direct string equality between the requested value and readback value:

- expected write value might be ""0"" or ""1""
- readback often returns driver display text such as:
  - "Disabled"
  - "Enabled"
  - "Rx & Tx Enabled"

That means the write can succeed but verification still fails incorrectly.

2. "readNicProperty()" currently reads "DisplayValue", not a stable raw value
   This is not safe for verification because display values vary by:

- driver vendor
- localization
- adapter model
- Windows version

Readback must include both:

- "RegistryValue"
- "DisplayValue"

3. "resetNicProperty()" is using a derived DisplayName from the RegistryKeyword
   Current logic:

- discovers the real registry keyword
- then strips "*"
- then uses that as DisplayName for reset

This is not reliable because actual driver DisplayName often does not equal the RegistryKeyword with "*" removed.

4. The current NIC path is still vulnerable to false failures on adapters where:

- the property exists
- the write succeeds
- but display/readback formatting differs

Required fixes:

1. Upgrade NIC readback
   Change "readNicProperty()" so it returns:

- actual "RegistryValue"
- actual "DisplayValue"
- actual discovered "RegistryKeyword"
- actual discovered "DisplayName"

2. Add normalized verification
   Do not verify with raw string equality only.
   For toggle and stepped properties, normalize values.

Examples:

- ""1"" should match "Enabled"
- ""0"" should match "Disabled"
- ""3"" should match "Rx & Tx Enabled"

Use property-aware normalization for:

- RSS
- InterruptModeration
- EEE
- FlowControl
- GreenEthernet
- any other stepped/toggle NIC fields

3. Fix reset path
   Do not derive DisplayName from RegistryKeyword.
   Instead:

- discover the actual property object for that adapter
- use the actual returned DisplayName if Reset-NetAdapterAdvancedProperty requires DisplayName
- otherwise use the most stable supported identifier possible

4. Improve result reporting
   Return distinct outcomes:

- unsupported_on_adapter
- elevation_denied
- write_failed
- write_succeeded_verify_failed
- write_succeeded_verified
- reset_failed
- reset_verified

Do not collapse everything into one generic failure.

5. Audit the main Network Tweaks page too
   The shared failure across all network tweaks is still likely in the frontend action path, not only NIC tuning.
   Audit the actual React component that calls:

- "window.electronAPI.networkTweaks.execute(...)"

Confirm the action names sent are exactly:

- "apply"
- "revert"

because the executor and preload only accept those values.

Return:

- exact file changes
- exact normalization logic added
- exact reset fix
- exact network tweak frontend action mapping
- proof that settings work on at least:
  - Realtek
  - Intel
  - one alternate vendor/driver path if available
