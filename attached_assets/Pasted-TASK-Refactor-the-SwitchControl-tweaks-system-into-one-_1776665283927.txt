TASK

Refactor the SwitchControl tweaks system into one canonical, production-grade architecture that is fully aligned across frontend, backend, execution, verification, premium gating, intelligence, and UI.

This is not a small patch.

This is a structural cleanup and upgrade.

We need the tweaks system to become:

- one source of truth
- fully honest
- slider-capable
- execution-aligned
- trustworthy in UI and backend
- ready for real public users

We are not doing half-cleanup.
We are not keeping duplicate tweak systems.
We are not showing fake or unsupported tweaks as if they are real.
We are not keeping fragmented logic where different files disagree.

The final result must feel excellent, not just acceptable.

PROBLEM

The current tweaks architecture is fragmented.

Right now the system is split across too many disconnected truth sources:

- mock-data.ts
- tweak tiers files
- tweak intelligence
- tweak executor
- tweaks UI
- premium gating
- unsupported tweak handling

This creates real problems.

1. mock-data.ts is acting like source of truth when it is not

It currently defines:

- tweak ids
- titles
- descriptions
- risk
- level
- category
- expected impact
- reboot flags

But real execution truth lives somewhere else.

That means the UI can drift away from backend reality.

That is already happening.

2. Some tweaks are shown like they are real, but they are not truly supported

Examples include:

- p-states
- irq-priority
- timer-res
- desktop-comp
- hdcp

These are currently exposed in a way that overstates certainty.

That is bad trust design.

If a tweak is unsupported, requires an agent, is conditional, or is not honestly implementable, the app must say so clearly and architecturally.

3. The tweak registry is duplicated

We currently have multiple places defining tweak identity and behavior.
That is weak architecture and guaranteed drift.

4. The current tweak model is mostly toggle-only

That is no longer enough.

We now need real numeric controls for certain advanced tweaks.

The current model is not built cleanly for:

- sliders
- actions
- conditional support
- prerequisites
- advanced warnings
- hardware-dependent support
- precise free vs premium gating

5. The executor is stronger than the catalog in some places, but weaker in others

Some parts of tweak-executor.js are clearly more mature and honest than the UI definitions.
But the app still allows outdated or misleading presentation because the display layer is not truly driven by execution truth.

6. Tweak intelligence can rank things that are not cleanly supported

That must stop.

The recommendation system must only recommend:

- real supported tweaks
- conditionally supported tweaks only when valid
- no fake or agent-only tweak unless clearly marked and intentionally surfaced

7. Premium gating is fragmented

Tier logic is defined in multiple places.
This is another drift problem.

8. The current UI is good visually, but the data model underneath is not mature enough

The UI wants to feel premium, but the underlying tweak system is still closer to a manually curated catalog than a canonical system.

That mismatch will bite later.

GOAL

After this refactor, the tweaks system must have:

1. One canonical tweak registry

A single authoritative registry that defines tweak metadata for the whole app.

2. Honest support status

Unsupported or agent-required tweaks must never be presented as ordinary real tweaks.

3. Slider support

The tweaks system must support real sliders for advanced tweak values.

4. Execution alignment

Frontend tweak cards, toggle states, sliders, tiers, and intelligence must all map to the same tweak IDs and support model.

5. Clean premium gating

Free vs premium must come from the same canonical registry, not from scattered logic.

6. Real recommendation integrity

Tweak intelligence must only recommend supported and valid tweaks.

7. Stronger UX trust

If something is unsupported, conditional, admin-only, reboot-required, or risky, the UI must reflect that honestly.

8. Better product quality

This should feel like a real mature optimization engine, not a set of loosely connected tweak cards.

ARCHITECTURE DECISION

Create a single canonical tweak registry and make everything consume it.

This registry becomes the source of truth for:

- UI title
- description
- category
- level
- risk
- control type
- support status
- premium tier
- requires admin
- requires reboot
- requires agent
- visibility
- warnings
- slider config
- backend execution key
- recommendation eligibility

All other tweak systems must reference this registry instead of redefining tweak meaning.

The executor remains responsible for:

- apply
- revert
- verify
- elevate
- logs
- failure classification

But it must use the same tweak ids and same registry contract.
