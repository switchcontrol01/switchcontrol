TASK
Implement a real backend execution system specifically for Network Tweaks so every network tweak actually applies on the system instead of being UI-only.

GOAL
Make all Network Tweaks functional, real, and verifiable.

This includes:
- applying real system-level network changes
- using correct Windows commands (PowerShell / netsh / registry)
- handling admin privileges properly
- verifying changes after execution
- returning real success/failure states to frontend

IMPORTANT
Do NOT modify other tweak systems (Tweaks page already works).
Do NOT redesign UI.
Do NOT fake execution.
Do NOT mark success without real verification.
This task is ONLY for Network Tweaks backend execution.

SCOPE
Only affects:
- Network Tweaks page
- Network tweak toggle cards
- Backend execution for network-related changes

IMPLEMENTATION

1. CREATE NETWORK TWEAK EXECUTOR
Implement a dedicated backend module for network tweaks.

Example:
- backend/network-tweak-executor.ts
or similar

This module must:
- receive tweak id + desired state (enable/disable)
- map tweak id to actual system command(s)
- execute command
- verify result
- return structured response

2. DEFINE REAL NETWORK TWEAK ACTIONS
For each existing network tweak in the UI (SMB, TCP/IP, UDP, DNS, etc):

Map them to real system-level operations using:

- PowerShell
- netsh
- registry (HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters etc)
- Windows features (SMB1/2/3)
- service configuration where needed

Example types of real actions:
- enabling/disabling SMB versions
- adjusting TCP parameters
- modifying network buffer limits
- adjusting autotuning settings
- enabling/disabling offloads
- changing congestion provider
- setting network throttling index
- adjusting IRP stack size
- etc

IMPORTANT:
Only use REAL, documented, and safe system-level changes.
No fake or placebo tweaks.

3. ADMIN EXECUTION FLOW
Network tweaks often require admin.

Ensure:
- commands run via Electron main process or backend with elevation
- failure due to permissions is caught and returned
- frontend gets proper error message if admin required

Do NOT silently fail.

4. COMMAND EXECUTION LAYER
Use a clean execution wrapper:

- run PowerShell / CMD commands
- capture stdout / stderr
- handle exit codes
- timeout protection

Return structured result:
- success
- failure
- error message
- raw output (optional for logs)

5. VERIFICATION STEP (CRITICAL)
After applying a tweak, verify it.

Examples:
- read registry value back
- query netsh state
- check Windows feature state
- confirm service config

If verification fails:
→ return failure (NOT success)

6. CONNECT FRONTEND TO BACKEND
Fix the Network Tweaks UI so:

When toggle is changed:
1. send request → backend
2. show “applying” state
3. wait for result
4. update UI ONLY after success
5. show error if failed

Do NOT:
- instantly flip toggle visually
- assume success

7. HANDLE ON/OFF STATES PROPERLY
Each tweak must support:

- enable (apply tweak)
- disable (revert tweak)

If revert is not possible:
- mark tweak as one-way
- do NOT fake toggle back

8. STANDARD RESPONSE FORMAT
All network tweak executions should return:

- tweakId
- action (enable/disable)
- success (true/false)
- verified (true/false)
- message
- requiresRestart (if applicable)

Frontend must use this.

9. LOGGING
Add logging for network tweak execution:

- tweak id
- command run
- result
- error (if any)
- timestamp

Useful for debugging and credibility.

10. DO NOT IMPLEMENT FAKE TWEAKS
If any current network tweak cannot be safely implemented:

- disable it
or
- mark as “not available yet”

Do NOT leave fake toggles.

CHECKLIST
- network tweak executor created
- each network tweak mapped to real system commands
- admin execution works
- verification implemented
- frontend wired correctly
- toggles reflect real state
- failures handled properly
- no fake tweaks remain

FINAL OUTPUT
Return:
1. network tweaks implemented
2. backend executor details
3. commands used per tweak
4. verification methods used
5. admin execution flow
6. any tweaks not implementable
7. files changed

11. AUDIT TWEAK VALIDITY BEFORE IMPLEMENTING
Before wiring every network tweak, audit the current Network Tweaks catalog.

For each tweak, determine:
- whether it is real and implementable
- whether it is safe enough to expose
- whether it duplicates another tweak
- whether it has a real revert path
- whether it is OS/version/hardware dependent

If a tweak is:
- fake
- placebo
- duplicated
- unsafe without enough value
- not realistically verifiable

then do NOT implement it blindly.
Disable it, merge it, or mark it unavailable with a clear reason.

Do not preserve bad tweaks just because they already exist in the UI.
