TASK

Fix tweak state correctness for the main Tweaks page. Some tweaks are visually inconsistent and some are being shown as enabled even when verification fails.

PROBLEM

Two bugs are happening:

1. Disable Hibernation appears to execute, but the toggle/card UI does not update smoothly or correctly after click.
2. Disable Maintenance is a real verification failure:
   - command runs
   - post-check says state did not change
   - UI can still look enabled or partially enabled

This means the tweak system is confusing:

- command execution success
- actual system state change
- UI enabled state

That is wrong for a production tweak app.

GOAL

Make tweak cards truthful and deterministic:

- if command runs but verification fails, do NOT show enabled
- if apply/revert succeeds, UI must update cleanly and immediately
- no stale state re-hydration should overwrite a fresh result
- no tweak should appear enabled unless verification or authoritative state check confirms it

FILES TO CHECK

- client/src/pages/Tweaks.tsx
- client/src/components/TweakCard.tsx
- client/src/hooks/use-tweak-executor.ts
- electron/tweak-executor.js
- any tweak status store / persistence store used by Tweaks page
- the specific tweak definitions for:
  - Disable Hibernation
  - Disable Maintenance

SECTION 1 — FIX UI STATE MODEL

Audit the full state path for a tweak click:

- user clicks toggle
- IPC execute runs
- backend returns success / verified / message
- frontend updates card state
- any refresh or persisted-state hydration runs after that

Hard rule:

- verified success = enabled
- verified revert = disabled
- execution success but verification failed = failed/unverified state, NOT enabled
- stale backend or persisted refresh must never overwrite a fresh local result unless a new authoritative re-check confirms it

SECTION 2 — FIX HIBERNATION CARD BEHAVIOR

Investigate Disable Hibernation specifically.

Symptoms:

- click does not visually slide/update properly
- toast may indicate success/revert, but card state is inconsistent

Check for:

- toggle using wrong source of truth
- non-optimistic state mixed with delayed refresh
- immediate re-fetch overwriting result
- animation boolean bound to stale prop instead of current stateMap result

Need result:

- click hibernation on/off
- card updates once
- toggle position matches latest verified state
- no bounce-back unless real verify fails

SECTION 3 — FIX DISABLE MAINTENANCE COMMAND + VERIFY

Investigate Disable Maintenance specifically.

Current evidence says:

- command runs
- verify fails
- system state may not actually change

Need full audit of:

- exact apply command
- exact revert command
- exact verify command
- whether the command writes the correct registry/task path
- whether Windows Scheduled Maintenance is controlled by multiple flags/tasks/services
- whether Defender / Task Scheduler / maintenance scheduler re-enables it

Do not just suppress the error.
Fix the real root cause.

If this tweak cannot be implemented reliably across normal Windows systems:

- mark it unavailable
- explain why
- do not pretend it works

SECTION 4 — NO FALSE ENABLED STATES

Make this a hard invariant for all tweaks:

- execution success alone must never light the card as enabled
- only verified state or authoritative readback can do that
- verification failure must show:
  - failed/unverified status
  - clear message
  - toggle visually returned to real state

Return:

- exact root cause for Disable Hibernation UI inconsistency
- exact root cause for Disable Maintenance verification failure
- exact files changed
- before/after state logic
- confirmation that a tweak can no longer appear enabled when the system did not actually change
