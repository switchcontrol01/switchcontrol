TASK: Diagnose and fix Electron Google login loop and false "login canceled" state

PROBLEM

The Electron Google login flow is currently broken in a real user-facing way.

Observed behavior:

1. In the Electron app, user clicks:
- Continue with Google

2. System browser opens correctly.

3. User selects Google account successfully.

4. Instead of completing login inside the Electron app, the flow loops / stalls.

5. The app does not complete authenticated state properly.

6. After waiting, the app shows:
- "login canceled"

7. The browser side appears to authenticate, but the app-side handoff/finalization is failing.

This means the login process is not actually completing end-to-end inside Electron even though the browser auth step is being reached.

GOAL

Find the exact cause of the Electron login loop / stalled auth / false "login canceled" state and fix it properly.

Correct behavior must be:

Electron app
→ user clicks Continue with Google
→ system browser opens
→ user signs in with Google
→ backend callback succeeds
→ browser redirects back to switchcontrol:// deep link
→ Electron app receives callback
→ Electron validates callback payload
→ Electron exchanges code/token if needed
→ Electron commits authenticated session state
→ user becomes logged in inside the app

If login genuinely fails or is cancelled, the app should show the correct reason.
It must not falsely say "login canceled" when auth actually succeeded in browser but failed in the handoff/finalization layer.

IMPLEMENTATION

SECTION 1 — TRACE THE FLOW END-TO-END

Inspect the full login chain from start to finish:

- Electron login button handler
- system browser open logic
- Google auth start URL
- backend auth source preservation
- backend Google callback
- deep-link redirect generation
- Electron deep-link listener
- callback parsing
- exchange endpoint if present
- local authenticated state commit
- loading/error/cancel state transitions

Do not guess.
Find the exact stage where the login stops completing.

SECTION 2 — IDENTIFY THE ACTUAL FAILURE POINT

Determine which of these is happening:

A. Browser auth succeeds, but backend never redirects to deep link  
B. Backend redirects to deep link, but Electron is not receiving it  
C. Electron receives deep link, but callback parsing fails  
D. Electron parses callback, but exchange endpoint fails  
E. Exchange succeeds, but renderer/app state never updates to logged-in  
F. Auth timeout/cancel logic is incorrectly firing even after partial success  
G. Existing login flow has race conditions between success and cancel/error handlers

Report the exact failure point, not just symptoms.

SECTION 3 — VERIFY DEEP LINK REGISTRATION AND HANDLING

Inspect the Electron custom protocol flow.

Confirm:
- app is properly registered to handle `switchcontrol://`
- deep links are received both when app is already open and when app is launched by protocol
- callback route like `switchcontrol://auth/callback?...` is handled correctly
- malformed payloads are rejected safely
- valid payloads continue the login process

Check for bugs such as:
- protocol handler registered incorrectly
- listener only works on cold launch but not warm app state
- listener fires but data is discarded
- callback path mismatch
- query parsing mismatch
- second-instance/deep-link handling bug
- success callback not forwarded from main process to renderer

SECTION 4 — VERIFY BACKEND CALLBACK HANDOFF

Inspect the backend Google callback behavior.

Confirm:
- successful Electron auth does not stop at browser login only
- callback detects Electron source correctly
- backend actually issues deep-link redirect for Electron flow
- redirect uses the correct format
- one-time handoff code/token is valid and not immediately rejected
- callback is not accidentally falling back to website redirect or dead-end page

If source preservation is broken, fix it using the existing intended auth-source mechanism.

SECTION 5 — VERIFY ELECTRON SUCCESS PATH

Inspect what happens after Electron receives auth callback.

Confirm:
- callback payload is accepted
- exchange endpoint is called if required
- successful response reaches the renderer/store/auth state
- local auth persistence is written correctly
- authenticated user state is committed
- loading state is cleared
- app UI transitions from login screen to authenticated state

Do not stop at "callback received".
The app must actually become logged in.

SECTION 6 — FIX FALSE CANCEL / TIMEOUT STATE

The app currently ends up showing:
- "login canceled"

This may be false.

Audit all logic that can trigger:
- cancel
- timeout
- aborted auth
- cleanup/reset
- loading fallback

Fix any case where:
- browser auth partially or fully succeeds
- but a timeout/cancel handler still fires afterward
- and overwrites the success path or final status

Success must win over cancel if auth completion actually happened.
Cancel should only display when the user truly cancels or the flow definitively aborts.

SECTION 7 — REMOVE LOOPING BEHAVIOR

Prevent login restart loops caused by:
- auth state not committing after success
- retry logic firing automatically
- app returning to login screen without clearing pending auth state
- stale loading flags
- browser callback not resolving pending auth promise
- renderer assuming login failed before deep-link handoff completes

There must be one clear auth attempt lifecycle:
- start
- waiting
- callback received
- exchange
- success OR fail/cancel
- cleanup

No duplicate overlapping attempts.

SECTION 8 — ADD SAFE DEBUG LOGGING

Add temporary or safe structured logging for the full Electron auth flow:

- login start
- browser launched
- callback route hit on backend
- deep-link redirect issued
- deep-link received in Electron
- callback parsed
- exchange requested
- exchange result
- auth state committed
- cancel/timeout triggered
- final UI status

Do not log:
- JWTs
- raw OAuth tokens
- secrets

Safe fields only:
- requestId
- stage
- source
- result
- safe failure reason

Use this logging to prove exactly where the flow breaks.

SECTION 9 — VERIFY BOTH APP STATES

Test deep-link handling in both cases:

1. Electron app already open when login completes
2. Electron app reopened/launched by protocol after browser callback

Both must work.

A common bug is that only one of these states works.

SECTION 10 — CLEAN ERROR HANDLING

Final behavior must be:

If success:
- user is logged in
- no cancel message
- no stuck spinner
- no loop

If failure:
- show accurate failure message

If actual cancel:
- show accurate cancel message

Do not collapse all failures into "login canceled".
