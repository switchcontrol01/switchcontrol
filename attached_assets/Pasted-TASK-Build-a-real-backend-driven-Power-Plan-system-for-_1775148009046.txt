TASK

Build a real backend-driven Power Plan system for SwitchControl so the Power Plan page is no longer a visual shell. The backend must own truth, apply real Windows power settings, verify them after apply, and return normalized data that drives the UI.

PROBLEM

The current Power Plan page looks premium, but it does not behave like a real power management system yet.

Current issues:

Profile cards appear to be mostly frontend-driven instead of backend-verified

“Active” state can become cosmetic instead of reflecting real Windows power state

Breakdown labels look static rather than derived from actual system values

There is no clear single backend service that owns power plan logic

The page risks becoming misleading if users click Activate Profile and the system does not actually verify changes


This must be fixed so:

the backend reads the real active Windows power plan

presets map to actual Windows powercfg values

the app applies them through Electron

the backend re-reads and verifies what was actually applied

the UI renders only backend-confirmed truth


GOAL

Create a production-grade Power Plan backend service in Electron with these outcomes:

1. Detect the real currently active Windows plan and relevant setting values


2. Define real preset profiles for:

Maximum Performance

Balanced Gaming

Efficiency / Laptop



3. Apply profiles through Windows powercfg commands


4. Verify applied settings after activation


5. Return normalized JSON to the frontend


6. Make the Power Plan page render backend truth only


7. Remove fake / decorative “active” behavior that is not tied to backend verification



IMPLEMENTATION

1. Create a dedicated Electron backend service



Create a new backend file:

electron/power-plan-manager.js


This file must own all power plan logic.

Implement these functions:

listPowerSchemes()

getActivePowerScheme()

readPowerSettingsForScheme(schemeGuid)

applyPowerProfile(profileId)

applyIndividualPowerSetting(settingKey, value, powerSource)

verifyPowerProfile(profileId)

mapSystemStateToProfile(currentSettings)


Do not scatter power plan logic across generic tweak handlers unless absolutely necessary.

2. Expose typed preload APIs



In preload.js, expose a dedicated power plan API namespace, for example:

window.electronAPI.powerPlans.list()

window.electronAPI.powerPlans.getActive()

window.electronAPI.powerPlans.getDetails(profileId)

window.electronAPI.powerPlans.applyProfile(profileId)

window.electronAPI.powerPlans.applySetting(settingKey, value, source)

window.electronAPI.powerPlans.verify(profileId)


These should IPC into the new power-plan-manager service.

3. Add IPC handlers in electron/main.js



Register IPC handlers that forward requests into the new manager.

Expected handlers:

powerPlans:list

powerPlans:getActive

powerPlans:getDetails

powerPlans:applyProfile

powerPlans:applySetting

powerPlans:verify


Keep all return values normalized and frontend-safe.

5. Use real Windows powercfg commands



Implement the backend using powercfg first.

Required capabilities:

list all schemes

detect active scheme

read setting values

set active scheme

set AC values

set DC values where relevant

re-activate or refresh scheme after writes if needed


Use commands such as:

powercfg /list

powercfg /getactivescheme

powercfg /query

powercfg /setacvalueindex

powercfg /setdcvalueindex

powercfg /setactive


Avoid registry edits unless there is no clean powercfg path.

6. Build a normalized parser layer



Powercfg output is ugly. Parse it once centrally in power-plan-manager.js.

Create helpers like:

parseSchemeList(output)

parseActiveScheme(output)

parseQueriedSetting(output)

normalizeBoostMode(value)

normalizeCoreParking(value)

normalizeSleepValue(value)


Return frontend-ready objects, not raw command output.

7. Backend must verify after apply



After applyProfile(profileId):

re-read active scheme

re-read all relevant managed settings

compare against intended preset

return:

success

verified true/false

mismatched keys

active scheme guid

actual values

normalized breakdown



If not fully matched, return partial success with reasons. Never blindly return success.

8. UI must be driven by backend truth only



Update the Power Plan page so:

active card highlight comes from backend getActive / verify result

“Activate Profile” only becomes “Active” after backend confirmation

breakdown cards are populated from backend-derived labels

no hardcoded fake state survives after refresh


Do not let last-clicked frontend state define truth.

9. Breakdown section must become dynamic



The “Configuration Breakdown” area should be generated from normalized backend values, for example:

{
  cpuBoost: "Enabled when under load",
  sleepHibernate: "After 30 minutes idle",
  coreParking: "Minimal parking allowed",
  frequencyScaling: "Dynamic based on demand",
  usbPowerSaving: "Selective suspend disabled"
}

These labels must be computed from real applied values, not static marketing text.

10. Support exact, close, and custom profile matching



Implement profile matching carefully.

The system should be able to classify current state as:

exact_match

close_match

custom_modified

unknown


Do not require every unrelated Windows setting to match exactly. Match only on the fields SwitchControl manages.

11. Add safe error handling and logging



Add backend logs for:

scheme list read

active scheme read

each setting apply

verification pass

mismatch summary

powercfg failures


Return clean errors to UI:

failed to read schemes

failed to apply setting X

active scheme mismatch after apply

verification incomplete


12. Frontend behavior requirements



Power Plan page must:

fetch current backend power state on load

render loading state until backend returns

render true active profile

render custom state if system no longer matches a preset

refresh after apply

never assume success without backend verification


13. Keep scope tight



Do not bloat this task with unrelated tweaks, registry hacks, or extra animations.

Focus only on making Power Plan real, trustworthy, and backend-driven.
