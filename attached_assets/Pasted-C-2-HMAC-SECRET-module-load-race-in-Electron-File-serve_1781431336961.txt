C-2: HMAC_SECRET module-load race in Electron

    File: server/auth/google.ts
    Lines: const HMAC_SECRET = (process.env.JWT_SECRET || process.env.SESSION_SECRET || "").trim();
    Impact: If this module loads before desktop-secrets.ts populates env vars, the HMAC secret is the public default string. Any attacker with the source code can forge one-time auth codes.
    Exploitability: Medium — requires knowing the app uses the default, and the codes expire in 2 minutes.
    Fix: Make HMAC_SECRET a getter function that reads process.env at call time, matching the pattern used in server/lib/jwt.ts.

C-3: DevTools enabled in production Electron

    File: electron/main.js
    Lines: devTools: true in BrowserWindow options; F12/Ctrl+Shift+I explicitly enabled.
    Impact: Any user can open the DevTools console, inspect network requests, read IPC messages, and modify renderer state.
    Exploitability: High — trivial for any user.
    Fix: Set devTools: isDev || allowDebug and only open DevTools conditionally.

HIGH ISSUES

H-1: Premium API routes missing server-side enforcement

    Files: server/routes.ts
    Routes: /api/cleaner, /api/focus, /api/network-tweaks, /api/app-booster
    Impact: Free users can call premium-gated server functionality directly.
    Exploitability: High — any authenticated free user can POST to these endpoints.
    Fix: Add requireCloudPremium middleware to all premium-gated route groups.

H-2: x-electron-uid trust without cryptographic proof

    File: server/middleware/requireCloudAuth.ts
    Lines: The isElectronBackend fast-path accepts any x-electron-uid matching the regex.
    Impact: Any process on 127.0.0.1 can impersonate any user to the local backend.
    Exploitability: Requires local code execution — moderate. Mitigated by cloud-truth route blocking.
    Fix: Sign the UID with the shared desktop-secrets.ts JWT secret, or verify a short-lived local session token instead.

H-3: Trial users blocked from marking unlock/tour seen

    File: server/auth/google.ts
    Lines: /api/premium/unlock-seen and /api/premium/tour-seen check dbUser.isPremium not resolveEffectivePlan.
    Impact: Trial users get 400 errors and cannot dismiss animations, causing repeated display.
    Exploitability: Not a security issue, but a significant UX regression for trial users.
    Fix: Replace if (!dbUser.isPremium) with if (resolveEffectivePlan(dbUser) === 'free').

MEDIUM ISSUES

M-1: Client-side trial entitlement

    File: client/src/lib/entitlementResolver.ts
    Impact: Trial active/expired state determined by Date.now() on the client, not verified by the server.
    Fix: Add a server-side check on trial expiry for API access, or accept the UI-only risk as intended.

M-2: Offline device lock indeterminate state

    File: client/src/hooks/usePremiumDeviceLock.ts
    Impact: If the cloud is unreachable, the device lock check hangs indefinitely with isChecking: true. The DeviceLockModal is not shown (correct) but premium features remain accessible without validation.
    Fix: Add a timeout (e.g., 10 seconds) after which offline users are granted a grace period with a visible warning.

M-3: unsafe-inline in CSP

    File: server/index.ts
    Lines: scriptSrc: ["'self'", "'unsafe-inline'", ...]
    Impact: Significantly weakens XSS protections on the payment-handling web app.
    Fix: Migrate inline scripts to external files and remove unsafe-inline from scriptSrc.

M-4: Already-premium checkout not blocked by plan resolution

    File: server/routes.ts
    Lines: if (dbUser.isPremium) check in checkout creation
    Impact: Users on admin-granted premium (plan='premium', isPremium=false) can initiate payment.
    Fix: Replace with if (resolveEffectivePlan(dbUser) !== 'free').

LOW ISSUES

L-1: requirePremium legacy middleware uses raw isPremium

    File: server/auth/google.ts
    The requirePremium export checks req.user.isPremium from the Passport session, which doesn't go through resolveEffectivePlan. If used anywhere outside of legacy routes, it could fail to recognize trial/admin-granted premium users.
    Fix: Either remove it or rewrite it to call storage.getUser and resolveEffectivePlan.

L-2: /api/premium/reset-tour-flags has no premium check

    File: server/auth/google.ts
    Any authenticated user can reset their own tour flags. Low severity but inconsistent.

L-3: Device ID entropy

    File: electron/main.js
    getOrCreateDeviceId() truncates a UUID to 16 hex chars (64 bits). Sufficient for collision resistance but lower than a full UUID.

L-4: Stripe checkout keyGenerator fallback to IP

    File: server/routes.ts
    req.cloudUser?.id || req.user?.id || req.ip — if requireJwt passes but req.cloudUser is somehow null, rate limiting falls back to IP, which is bypassable with proxies.

Decision: NO — DO NOT LAUNCH IN CURRENT STATE

Reasoning:

The auth foundation is solid — HMAC-signed one-time codes, JWT issuer pinning, constant-time comparison, algorithm pinning, and a startup self-test are all good practices. The device lock design is architecturally sound.

However, three issues make launch premature:

    The premium success page doesn't actually grant premium. A paying customer completes checkout, lands on the success page, sees "Premium Activated," but may still be on the free tier. This is the most visible user-facing failure mode for a paid product.

    Multiple premium-gated server routes have no server-side enforcement. Free users can call cleaner, focus mode, network tweaks, and app booster APIs directly. The UI gates these features, but any technically-inclined user can bypass the UI.

    DevTools are enabled in production Electron builds. Every user can open the console and inspect the running app. For a product handling payments and system-level access, this is unacceptable.

The minimum viable fixes before launch are C-1, C-3, and H-1. C-2 and H-2 should follow immediately after. The remaining issues can be addressed in the first post-launch patch cycle.
