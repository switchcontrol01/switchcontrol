TASK

Fix the Electron startup architecture and renderer polling so one non-critical crash can never break app startup again, and so the renderer never spams dead IPC handlers or backend checks.

This is not just an fs fix. This is a startup hardening pass.

PROBLEM

Current known failure pattern:

1. A non-critical block inside "app.whenReady()" throws
2. The rest of "whenReady()" stops running
3. Critical IPC handlers never register
4. Renderer keeps polling missing handlers
5. App looks broken, can lag, and can require multiple launches

We already confirmed one real regression was:

- "ReferenceError: fs is not defined"

But the real weakness is architectural:

- critical startup logic is mixed with risky/non-critical startup logic
- renderer polling does not fail safely
- missing backend or missing IPC causes repeated polling spam instead of graceful backoff
- updater/backend/admin handlers are too easy to lose if startup throws

GOAL

Make startup bulletproof.

Required outcome:

1. Critical IPC handlers always register first
2. Non-critical startup code can never kill app startup
3. Renderer must stop fixed-interval spam when IPC or backend is unavailable
4. Backend readiness and renderer polling must use backoff, not aggressive loops
5. App must still open and function even if audit/non-critical startup code fails

IMPLEMENTATION

1. Split Electron startup into hard layers

Refactor "app.whenReady()" so it does NOT contain one giant mixed startup chain.

Create separate functions:

- "registerCriticalIPC()"
- "createMainWindowSafe()"
- "startBackendSafe()"
- "runStartupAuditSafe()"
- "registerNonCriticalIPC()" if needed

Required order:

A. registerCriticalIPC first
B. create window
C. start backend safely
D. run non-critical audit separately

Target structure:

app.whenReady().then(async () => {
  registerCriticalIPC();
  await createMainWindowSafe();
  await startBackendSafe();
  void runStartupAuditSafe();
});

Important:

- non-critical code must never block or kill startup
- "runStartupAuditSafe()" must be isolated from the critical path

2. Register critical IPC handlers before any risky code

These handlers must be registered immediately at the very top of startup, before any file reads, backend audit, restore audit, updater init, or other risky code:

- "app:getBackendPort"
- "app:isBackendReady"
- "app:getBackendError"
- "app:isAdmin"
- "updater:getState"

Also add a new handler:

- "app:isIPCReady"

Implementation idea:

let ipcReady = false;

function registerCriticalIPC() {
  ipcMain.handle('app:getBackendPort', ...);
  ipcMain.handle('app:isBackendReady', ...);
  ipcMain.handle('app:getBackendError', ...);
  ipcMain.handle('app:isAdmin', ...);
  ipcMain.handle('updater:getState', ...);
  ipcMain.handle('app:isIPCReady', () => ipcReady);
  ipcReady = true;
}

Important:

- remove duplicate registrations from later in startup
- do not leave old duplicate handler code behind
- no "Attempted to register a second handler" errors
