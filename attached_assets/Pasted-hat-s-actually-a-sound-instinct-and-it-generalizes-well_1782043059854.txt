hat's actually a sound instinct, and it generalizes well beyond just Driver Intelligence — worth applying as a principle across the app, not just this one feature.

## Why this is the right call

Looking back at everything we found: `tweak:batchCheckAll`, `SysIntelligence` deep collection, `storage:getVolumes`, GPU enrichment via `si.graphics()` — all of these currently fire automatically at startup, whether or not the user is even going to look at the Tweaks page, the BIOS Advisor, or the System Cleaner in that session. That's the actual source of the startup CPU spike and audio glitch. **The fix isn't "make the PowerShell calls faster" — it's "don't make calls for pages the user hasn't opened yet."**

Driver Intelligence should absolutely follow this same pattern: don't scan anything until the user navigates to that page. No 15-probe hardware scan should fire as part of app launch just because the feature exists.

## How this should work as a general pattern

**Lazy-load per page, not eager-load at startup.** Each page/feature owns its own data-fetch trigger, fired on mount, not bundled into a global startup sequence. This is partially already true for some things (Network Tweaks shows "cache fresh — skipping fetch" patterns), but `tweak:batchCheckAll` and `SysIntelligence` are still firing unconditionally at launch based on what we've seen in every log.

**Cache aggressively, with a visible "last scanned" state.** Once a user does open Driver Intelligence (or Tweaks, or BIOS Advisor) and a scan completes, cache the result with a timestamp. Next time they open that page in the same session — or even across sessions, with a reasonable TTL — show the cached result instantly with a "Scanned 2 hours ago — Rescan" button, rather than re-running the full probe set every single time they navigate there.

**Startup should only do the bare minimum needed for the dashboard itself.** Looking at what the dashboard actually displays (CPU/RAM/GPU live numbers, active problems, instability score), that's a much smaller set of probes than the full system intelligence sweep. Everything else — full hardware profile, driver versions, BIOS comparison, tweak verification against real Windows state — can wait for the user to ask for it by visiting that page.

## One nuance worth deciding

Some of your current startup-time scans exist specifically so that *other* things load fast later — e.g., `tweak:batchCheckAll` reconciles the Tweaks toggle states against real Windows state so that when the user does open Tweaks, it shows correct on/off states immediately rather than a loading flicker. If you defer that scan to "only when Tweaks page opens," the tradeoff is: faster startup, but a brief loading state the first time they open Tweaks each session (which is probably the right tradeoff, just worth being deliberate about rather than accidental).

> "Change the startup sequence so PowerShell/WMI-heavy scans (`tweak:batchCheckAll`, `SysIntelligence` deep collection, `storage:getVolumes`, and any future Driver Intelligence scan) only fire when the user actually navigates to the page that needs that data — not automatically on app launch. Cache results with a timestamp so repeat visits in the same session don't re-scan unless the user hits 'Rescan' or the cache is stale. The dashboard itself should only fetch what it actually displays at startup — nothing else. Confirm with before/after CPU/PowerShell-spawn timing in the logs that startup no longer has a cluster of PS-Exec calls firing in the first few seconds."

This single architectural change probably fixes the audio glitch, the perceived lag, and sets the right precedent for Driver Intelligence before it's even built — rather than building a 15-probe scanner and then having to retrofit the same lazy-loading fix onto it later.
