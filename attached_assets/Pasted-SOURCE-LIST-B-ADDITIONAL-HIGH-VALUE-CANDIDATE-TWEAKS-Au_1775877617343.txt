SPECIAL HANDLING / QUALITY RULES
Some candidate tweaks require special handling:

1. COMPOUND / PACK TWEAKS
If a tweak is better exposed as a premium compound pack instead of a low-value single toggle, that is allowed.

Examples:
- Input Stability Pack
- Background Recording Off
- Low-Latency Power Path
- Network Scheduling Pack
- USB Device Stability Pack

But:
- do NOT create these if they duplicate existing single toggles badly
- do NOT hide important logic from the user dishonestly
- keep the catalog clean

2. ADVANCED / DISCRETIONARY ONLY
Some candidate tweaks should only be added if clearly labeled as Advanced or Discretionary, not Recommended.

Examples likely needing stronger warning treatment:
- Disable Dynamic Tick
- Disable HAGS
- Disable Print Spooler
- Disable Windows Search Indexing
- Disable Idle States
- Disable Remote Registry
- Disable Windows Error Reporting
- Disable Delivery Optimization
- Disable Clipboard/Activity History class tweaks
- any risky GPU/display behavior toggles

3. REJECT LOW-VALUE OR JUNK TWEAKS
Do NOT add anything that is:
- placebo
- weak and unprovable
- dangerous without enough value
- duplicative of an existing tweak
- fake optimization fluff
- generic “gamer mode” nonsense

If a source tweak is weak, reject it and report why.

STEP 2: DETERMINE TRUE MISSING TWEAKS
From BOTH source lists above, identify ONLY the tweaks that are actually missing from SwitchControl.

Do not add:
- exact duplicates
- near-duplicates
- same backend effect under different wording
- low-value duplicate variants
- compound tweaks that just duplicate existing exposed tweaks with no added value

STEP 3: ADD ONLY THE TRUE MISSING TWEAKS
For each truly missing and worthwhile tweak:
- add frontend card
- add backend execution logic
- add verification logic
- add revert logic where possible
- add warning text if risky
- add OS / vendor / hardware guards where needed
- add category / label / risk classification
- make sure the UI matches the existing SwitchControl style

STEP 4: BACKEND MUST BE REAL
Every newly added tweak must have real backend logic.

Need:
- real apply action
- real revert action where possible
- real verification
- proper error handling
- privilege/admin handling
- honest result states

No simulated actions.

If a tweak cannot be safely or realistically implemented:
- do NOT fake it
- mark it unsupported and explain why
- or leave it out

Need:
- consistent naming

- consistent risk labeling
- consistent descriptions
