TASK
Fix the dashboard component state tracking so hardware information is cached on initial load and deep WMI queries are not repeated during route changes.
PROBLEM
Currently, navigating away from the dashboard and back (for example, Dashboard → Settings → Dashboard) causes the entire dashboard layout to remount.
Because the system specification metrics are bound tightly to this mount life-cycle, the underlying hardware query service invokes a full system inventory poll every single time. This re-triggers deep calls to local diagnostic layers (such as Windows Management Instrumentation) on every single navigation event.
This results in severe, repetitive micro-stutters and input response delays during active gameplay because the application repeatedly triggers a blocking system query thread. The metrics fetching should be executed as an initial application startup experience, not a localized route mount effect.
GOAL
The hardware query logic should:
 * Execute once when the desktop application officially boots up.
 * Never re-poll system queries when moving back and forth between navigation side-bars.
 * Never replay hardware detection loops when returning to the landing screen from Settings.
 * Maintain completely static, instantly cached state variables across all route switches.
 * Only allow a fresh evaluation if the entire application layer process has been terminated and fully initialized again.
ADDITIONAL IMPROVEMENT
Instead of risking thread locking via deep polling fallbacks on every minor data update:
 * Seed a high-priority quick hardware state cache immediately on bootstrap.
 * Match discovered system configurations against a curated dictionary of known premium gaming processors.
 * Persist this synchronized hardware profile safely for the duration of the execution window.
 * Serve subsequent dashboard mount instances using this lightweight memory store.
 * Re-authenticate or query the deeper instrumentation layer only upon a clean process launch.
Example hardware profile targets:
 * Processor family flags
 * Active core counts
 * Base platform clock limits
 * Video controller profiles
 * Thermal state thresholds
 * Active memory pools
IMPLEMENTATION REQUIREMENTS
 * Use session-bound memory or global state contexts so the inventory state survives component destruction.
 * Do not commit these real-time process specs to persistent localStorage profiles to avoid stale hardware reports across physical modifications.
 * Leverage an in-memory session mapping layer or a global main-process state sync.
 * Store:
   * initSpecsFetched
   * activeHardwareProfile
LOGIC
On dashboard component mount:
IF initSpecsFetched evaluates to true:
 * Bypass all underlying hardware inspection routines completely.
 * Immediately populate UI panels using the current session cache.
IF initSpecsFetched is null or false:
 * Trigger the rapid system inventory path.
 * Map the resulting hardware flags into activeHardwareProfile.
 * Display the layout data dynamically.
 * Immediately toggle initSpecsFetched to true before any page route adjustments take place.
VALIDATION
Verify:
 1. Clean application launch
   * System inventory runs a fast single pass.
   * Core specifications are safely mapped to memory.
 2. Dashboard → Settings → Dashboard
   * Dashboard views load instantly without layout stutter.
 3. Dashboard → Tweaks Panel → Dashboard
   * Background hardware poll usage reads 0%.
 4. Dashboard → Any internal routing view → Dashboard
   * System query threads are completely silent.
 5. Completely exit application process and relaunch
   * Cache safely invalidates.
   * Initial quick-detection process executes once more on boot.
SUCCESS CRITERIA
The dashboard hardware profile functions strictly as a launch-cached resource rather than an iterative page navigation query.
Users experience a flawless, zero-stutter interface response that preserves in-game processing priority throughout the entire desktop session.
