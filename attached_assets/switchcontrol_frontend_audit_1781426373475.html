C WebsiteShell double-animates every page with blur(14px) on mount
GPUFCPmain thread
▾
Affects: GPU compositing, perceived FCP Measurable: Yes — visible stutter on every route load Thread: GPU compositor
Every page wrapped in WebsiteShell starts with filter: blur(14px) animating to blur(0px) over 0.8s. Blur forces the browser to rasterize the entire page content off-screen, composite it, then re-rasterize per frame as the value changes. On a typical 1440p display this is 3–8ms of GPU work per frame — consuming most of a 60fps frame budget just to show the page exists. It also delays FCP by 800ms. The background WebsiteBackground also animates opacity separately, creating two simultaneous compositor layers.
Exact fix
// In WebsiteShell — replace blur with opacity-only transition // Before: initial={{ opacity: 0, filter: "blur(14px)" }} animate={{ opacity: 1, filter: "blur(0px)" }} transition={{ duration: 0.8, delay: 0.08 }} // After: initial={{ opacity: 0, y: 8 }} animate={{ opacity: 1, y: 0 }} transition={{ duration: 0.45, ease: [0.22, 1, 0.36, 1] }} // For WebsiteBackground wrapper — remove its own fade, it's covered by parent: // Delete the motion.div wrapper around WebsiteBackground entirely. // WebsiteBackground is position:fixed; it doesn't need to animate in.
C WebsiteBackground runs TWO RAF loops on scroll (mouse + scroll) plus setScrollY on every scroll event
CPUmain threadlayout
▾
Affects: Scroll jank, CPU, React re-renders Measurable: Yes — visible on mid-range hardware Thread: React main thread + compositor
WebsiteBackground calls setScrollY(window.scrollY) inside a RAF on every scroll event. This triggers a React re-render of the entire background on every scroll frame. The background contains ~15 child elements with inline style recalculations (parallaxOffset, beamFade, transform strings). Since the background is position:fixed, its re-renders don't affect layout, but they do force style recalc and composite updates on a large subtree every frame. The parallax offsets are also applied via style props on individual elements — each a separate compositor layer update.
Exact fix
// Move parallax to CSS custom property on the root element via imperative DOM: const bgRef = useRef(null); useEffect(() => { const onScroll = () => { const y = window.scrollY; bgRef.current?.style.setProperty('--scroll-y', y); }; window.addEventListener('scroll', onScroll, { passive: true }); return () => window.removeEventListener('scroll', onScroll); }, []); // Then in CSS: // .ws-bg-layer { transform: translateY(calc(var(--scroll-y, 0) * 0.08px)); } // This eliminates all React re-renders on scroll entirely. // Remove setScrollY state and the scrollRafRef — not needed.
C Features.tsx runs 3 simultaneous rAF animation loops when in view — TelemetryDashboard, two LiveLineChart instances
GPUCPU60fps drain
▾
Affects: Frame budget, CPU, GPU on Features page Measurable: Yes — GPU utilization visibly spikes Thread: Main thread + GPU
The Features page has TelemetryDashboard running a rAF loop at 60fps with setMetrics (4 state updates per tick), and two separate LiveLineChart SVGs each running their own rAF at 60fps calling setAttribute on SVG paths. All three are simultaneously active when the section is visible. That's 3 rAF loops × 60fps = 180 DOM mutations/second. TelemetryDashboard already has a frameCount % 5 throttle (12fps) and LiveLineChart has frameCount % 10 (6fps) but the loops themselves still consume rAF slots every frame even when skipping work — keeping the main thread active.

Add intersection guard before starting.
C MagneticTilt runs an unbounded rAF loop at 60fps always — even when user isn't hovering
CPUrAFbattery
▾
Affects: CPU on landing page, battery drain Measurable: Yes — easily visible in DevTools performance panel Thread: Main thread
MagneticTilt starts a requestAnimationFrame(tick) loop that runs continuously at 60fps doing spring interpolation math and el.style.transform writes on every frame — forever. The spring targets (targetX/targetY) are 0 when not hovering, so after a few frames currentX and currentY converge to ~0. But the loop never stops — it keeps computing += (0 - ~0) * 0.08 every frame and writing transform: perspective(1200px) rotateX(0.00deg) rotateY(0.00deg) to the DOM. This is ~60 forced style recalcs per second for zero visual output. The Hero mockup wraps HeroAppMockup which is your largest, most complex DOM subtree.
Exact fix
// Stop the loop when values are settled (within epsilon): const tick = () => { currentX += (targetX - currentX) * 0.08; currentY += (targetY - currentY) * 0.08; el.style.transform = `perspective(1200px) rotateX(${currentX.toFixed(2)}deg) rotateY(${currentY.toFixed(2)}deg)`; const settled = Math.abs(currentX) < 0.01 && Math.abs(currentY) < 0.01 && Math.abs(targetX) < 0.01 && Math.abs(targetY) < 0.01; if (!settled) rafId = requestAnimationFrame(tick); else rafId = null; }; // On mousemove — restart loop only if not already running: const onMove = (e) => { // ... compute targetX/targetY if (!rafId) rafId = requestAnimationFrame(tick); }; // On mouseleave — let the loop drain to 0 naturally (settled check handles it)

H BlueprintImageOverlay: 4 divs with blur:40px on decorative elements — permanent GPU compositor layers
GPUcompositor layers
▾
Affects: GPU memory, compositing frametime Measurable: Yes — 4+ extra compositor layers in DevTools Layers panel

H HeroTiltContainer applies blur() on scroll via direct style mutation — triggers layout + paint per frame
GPUscrollFPS
▾
Affects: Scroll smoothness on landing hero Measurable: Yes — DevTools "Recalculate Style" spikes on scroll
HeroTiltContainer sets el.style.filter = blur(${blur}px) on scroll. CSS filter on a large element (the entire hero section) forces a full repaint of that subtree on every frame because the browser cannot composite-only a filter change — it must re-rasterize. The existing RAF guard is correct, but the operation itself is expensive. At scroll speeds of 4–8px per frame the blur progresses from 0–10px, meaning continuous repaints of the hero for ~100 scroll frames. The opacity and translateY are fine (compositor-only), but the blur undoes the savings.
Exact fix
// Option A (best): Remove blur entirely — keep opacity + translateY only. // The fade-out is smooth and the parallax sells the depth without repainting. const update = () => { const progress = Math.min(1, Math.max(0, (y - fadeStart) / (fadeEnd - fadeStart))); el.style.opacity = String(1 - progress * 0.72); el.style.transform = `translateY(${(progress * -24).toFixed(1)}px)`; // Remove: el.style.filter line entirely }; // Option B: Use CSS transition on a class toggle instead of per-frame value: // Add class "hero-scrolled" at progress > 0.3, remove when back. // .hero-scrolled { filter: blur(6px); transition: filter 0.3s; } // This composites once per threshold cross, not per frame.

GPUFramer Motionbattery
▾
Affects: CPU/GPU on Pricing page, battery Measurable: Yes — Framer Motion WAAPI driver keeps running
Two glow orbs in the Pricing hero use animate: { scale: [1,1.06,1], opacity: [0.8,1,0.8] } and animate: { x: [0,-25,0], y: [0,25,0] } with repeat: Infinity and durations of 10–18s. Infinity : 0, ... }} // Also: add prefers-reduced-motion check: const prefersReduced = window.matchMedia('(prefers-reduced-motion: reduce)').matches; // Skip all decorative infinite animations for these users.

M ReleaseStory IntersectionObserver fires setActiveStep on every entry — unstable index on rapid scroll
React re-renderscroll
▾
Affects: Release story scroll jank Measurable: Minor — occasional flicker on fast scroll
ReleaseStory observes all 6 steps simultaneously with threshold:0.5. On rapid scroll multiple entries fire at once — the forEach loop picks the last one in document order, not the most-visible one. This can cause the active index to jump backward. Additionally, isActive = i === activeStep && !isMobile is recalculated inline on every render, and the card's border and background styles are computed from it — both causing Framer Motion to re-evaluate motion values.
