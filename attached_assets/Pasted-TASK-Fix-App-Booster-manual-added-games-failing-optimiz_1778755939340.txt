TASK
Fix App Booster manual-added games failing optimization actions.

PROBLEM
When manually adding a game, App Booster shows optimization actions but applying them fails with errors like:

Unknown action type "enable-high-perf-plan"
Unknown action type "enable-game-mode"
Unknown action type "visual-effects-low"

This only happens for manually added games.

Catalog/detected games work better.

ROOT CAUSE
Manual games are being treated like catalog games, but their optimization action IDs do not match backend-supported action IDs.

The frontend is sending display/template action IDs such as:
- enable-high-perf-plan
- enable-game-mode
- visual-effects-low

But backend action executor does not recognize those strings.

GOAL
Manual games must either:
1. Use a safe generic profile with backend-supported action IDs, or
2. Disable unsupported actions with clear UI.

No manual game should show actions that cannot run.

IMPLEMENTATION

1. Find App Booster manual game creation logic.

Likely files:
- AppBooster.tsx
- app-booster-data.ts
- app-booster-store.ts
- game-detection.ts
- main.js app booster IPC/backend handlers
- preload.js exposed APIs

2. Separate game source types:

type GameSource = "catalog" | "detected" | "manual";

Manual game record should look like:

{
  id: `manual-${crypto.randomUUID()}`,
  source: "manual",
  name,
  exePath,
  iconPath: null,
  catalogId: null,
  actions: GENERIC_SUPPORTED_ACTIONS
}

Do not copy official catalog metadata or actions.

3. Create one safe generic action map.

Frontend action IDs must match backend executor exactly.

Example:

const GENERIC_SUPPORTED_ACTIONS = [
  "power-plan-high-performance",
  "windows-game-mode-enable",
  "visual-effects-performance",
  "disable-nagle"
];

Only include actions that backend actually supports.

4. Backend must expose supported actions.

Add IPC/API:

appBooster:getSupportedActions

Return:

{
  actions: [
    "power-plan-high-performance",
    "windows-game-mode-enable",
    "visual-effects-performance",
    "disable-nagle"
  ]
}

Frontend must filter actions against this list before showing Apply.

5. Add alias mapping if you want backwards compatibility.

In backend executor:

const ACTION_ALIASES = {
  "enable-high-perf-plan": "power-plan-high-performance",
  "enable-game-mode": "windows-game-mode-enable",
  "visual-effects-low": "visual-effects-performance"
};

const normalizedActionType = ACTION_ALIASES[action.type] ?? action.type;

Then execute normalizedActionType.

6. Manual game apply behavior:

Before applying:
- validate exePath exists
- validate action type is supported
- skip unsupported actions
- show exact reason per skipped action

Do not show generic:
"Check admin permissions and try again"

If action type is unknown, show:
"Unsupported optimization action for manual game."

7. Fix manual icon handling.

Manual games should not use catalog icons.

Rules:
- If exe icon extraction works, use extracted icon.
- Else use initials/custom placeholder.
- Do not use official MSFS/Fortnite/Apex icons unless game is matched to that catalog entry.

8. Add logs.

Frontend:
[AppBooster] manual game created name=... exePath=... source=manual
[AppBooster] filtering actions source=manual before=... after=...
[AppBooster] apply action=... supported=true

Backend:
[AppBooster] supported actions loaded count=...
[AppBooster] normalize action from=enable-high-perf-plan to=power-plan-high-performance
[AppBooster] unknown action type=... source=manual

CHECKLIST
- Manual-added game no longer copies official catalog icon incorrectly.
- Manual-added game only shows supported generic actions.
- Apply no longer fails with unknown action type.
- Unsupported action gives clear message, not admin permission error.
- Detected/catalog games still work.
- Manual game can be removed/deleted.
