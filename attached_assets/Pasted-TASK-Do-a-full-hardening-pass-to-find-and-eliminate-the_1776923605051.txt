TASK

Do a full hardening pass to find and eliminate the PowerShell multiplication bug causing extreme CPU usage and runaway process count in the packaged SwitchControl app.

PROBLEM

A real packaged-user report strongly indicates uncontrolled PowerShell spawning:

- CPU usage spikes very high
- Task Manager shows PowerShell processes multiplying
- total process count climbs massively
- closing SwitchControl drops CPU and process count back down immediately

This means SwitchControl is spawning PowerShell from one or more overlapping loops, polling paths, retries, or repeated verification calls.

GOAL

Completely eliminate uncontrolled PowerShell spawning.

PowerShell must only run:

- on explicit user action
- on intentionally throttled one-shot checks
- behind strict single-flight locking
- with zero overlap
- with zero render-loop or mount-loop amplification

At idle, opening the app and sitting on a page must NOT create a stream of new PowerShell.exe processes.

- electron/nic-executor.js
- electron/network-tweak-executor.js
- electron/tweak-executor.js
- electron/focus-helper.js
- electron/main.js
- any telemetry helper
- any verification helper
- any route/page logic that indirectly triggers backend PowerShell through IPC

- setInterval(

- recursive retry

- verification loops
- mount-time useEffect calls
- repeated IPC calls that trigger PowerShell-backed reads

MANDATORY REQUIREMENTS

1. FIND THE EXACT ROOT CAUSE
   Do not stop at "possible causes".
   Identify the exact file, exact function, and exact repeated trigger path causing PowerShell multiplication.

For every root cause found, report:

- file
- function
- trigger source
- why overlap occurred
- why it multiplied instead of staying single-instance

2. SINGLE-FLIGHT LOCKS ON EVERY POWERSHELL PATH
   Every PowerShell-backed function must have hard overlap protection.

Required pattern:

let running = false;
if (running) return;
running = true;
try {
...
} finally {
running = false;
}

Rules:

- lock must be set before any await
- lock must release in finally
- no early return may bypass finally
- if multiple call sites feed the same expensive function, protect the shared inner function too

3. NO POWERSHELL IN HOT PATHS
   PowerShell must not run from:

- 1s or 5s live polling if avoidable
- render-driven state churn
- accordion open/close
- tab switches
- page mount loops
- auth-hydration loops
- focus/blur churn
- repeated verification for visual status only

If a live UI needs data, use:

- cached backend state
- in-memory snapshots
- TTL cache
- manual refresh
- slower native/non-PowerShell path if available

4. THROTTLE ALL PASSIVE READS
   Any passive read/check using PowerShell must have a minimum cooldown or cache.

Examples:

- NIC capability detection
- tweak verification
- telemetry fallback reads
- trigger checks
- adapter enumeration
- hardware status checks

These must not rerun repeatedly during:

- rerenders
- route changes
- repeated effect mounts
- UI expansion/collapse
- auth changes unless strictly necessary

5. TEMPORARY EXECUTION LOGGING
   Add temporary diagnostic logging around every PowerShell launch.

For each launch, log:

- file
- function
- reason
- timestamp
- whether a run was skipped because one was already active
- duration
- success/failure
