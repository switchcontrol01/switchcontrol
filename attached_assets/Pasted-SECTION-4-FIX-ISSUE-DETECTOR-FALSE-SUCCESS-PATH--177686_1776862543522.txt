SECTION 4: FIX ISSUE DETECTOR FALSE-SUCCESS PATH
==================================================

PROBLEM
IssueDetector throws internally but still returns 200 with empty issues. That is fake success.

REQUIRED FIX
Issue detection must either succeed honestly or fail honestly.

IMPLEMENTATION
1. Find the code reading `.total` from an undefined object.
2. Add proper null guards before property access.
3. Replace broad fake-success fallback behavior with real error handling.

Pattern required:

try {
  // build issue data safely
} catch (err) {
  console.error('[IssueDetector] Fatal route error:', err);
  return res.status(500).json({
    ok: false,
    error: 'Issue detection failed'
  });
}

4. Validate every nested object before reading fields.
5. If some telemetry input is optional, handle it explicitly and degrade gracefully.
6. Do not swallow exceptions and return a 200.

ACCEPTANCE
- No IssueDetector TypeErrors in logs
- No 200 responses when detector crashes
- Route either returns valid issue data or a real 500
- Internal undefined access is eliminated

SECTION 5: STOP UNAUTHENTICATED ROUTE POLLING AND 401 SPAM
==================================================

PROBLEM
Frontend is calling protected endpoints before auth has finished restoring.

REQUIRED FIX
All protected route polling must wait for auth readiness.

IMPLEMENTATION

A. Add a real auth readiness state
Frontend must distinguish between:
- auth unknown / hydrating
- authenticated
- confirmed logged out

Do not let protected polling run while auth is unknown.

B. Protected fetch guard
For every protected hook/page:
- if authReady is false, do nothing
- if user is null, do nothing
- if token/session is absent, do nothing

C. Audit these surfaces at minimum:
- FocusMode
- Network Tweaks
- Cleaner
- App Booster
- any premium endpoints
- any user-history/state endpoints

D. If using React Query:
- use enabled: authReady && !!user
If using manual useEffect:
- early return unless authReady && user

E. Ensure polling intervals are not even created before auth is ready.

ACCEPTANCE
- No repeated 401s on cold startup
- No protected route polling before auth resolves
- Logs are clean during app boot
- CPU/network churn is reduced

SECTION 6: STARTUP ORDER HARDENING
==================================================

PROBLEM
Parts of the app are starting before required dependencies are ready.

REQUIRED FIX
Enforce correct boot order.

IMPLEMENTATION
1. Backend boot order
- config/env validation
- DB init
- auth/provider config snapshot
- route/module init
- server listen

2. Frontend boot order
- splash / bootstrap
- auth restore
- backend ready
- only then mount protected polling consumers

3. Add one central backend readiness flag if needed.
4. If the renderer relies on backend readiness, do not start polling until backend is confirmed ready.

ACCEPTANCE
- No route callers racing backend startup
- No modules initializing against missing dependencies
- No noisy first-boot request churn
