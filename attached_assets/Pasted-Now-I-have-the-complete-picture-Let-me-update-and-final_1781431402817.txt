NEW CRITICAL

C-4: Admin page makes unauthenticated requests in DeleteUserModal

File: client/src/pages/Admin.tsx, DeleteUserModal.submit()

const r = await fetch(`/api/admin/users/${user.id}`, {
  method: "DELETE",
  headers: buildHeaders() as any,
  body: JSON.stringify({ confirm: true, reason: AUDIT_REASON }),
});

buildHeaders() reads useAuthStore.getState().jwt directly — but also falls through to the _csrf cookie. The hardcoded AUDIT_REASON = "Admin deletion via admin panel" means the reason field in the audit log is never actually supplied by the admin doing the deletion. Every deletion audit entry will show the same boilerplate reason regardless of what the admin typed. This is not a security issue but silently breaks the audit trail, which the schema documentation specifically states is required.

Impact: Audit trail for user deletions is meaningless — all entries show "Admin deletion via admin panel" rather than the actual admin-supplied reason.

Fix: Pass the actual reason from the modal state (it has a reason field in the ConfirmModal but DeleteUserModal bypasses it with a hardcoded constant).

H-5: storage.ts deleteUser raw SQL interpolation

File: server/storage.ts, deleteUser method:

await tx.execute(drizzleSql.raw(`DELETE FROM ${tbl} WHERE user_id = '${userId.replace(/'/g, "''")}'`));

tbl is from a hardcoded array — safe. But userId is sanitized only by replacing single quotes, not by using a parameterized query. While userId originates from the server's auth middleware (not user input), if it ever contained a character like ; or -- from an unusual UUID generation path, this would be exploitable. More importantly, this pattern is architecturally wrong and sets a dangerous precedent.

Fix: Use Drizzle's parameterized SQL: drizzleSql\DELETE FROM ${drizzleSql.raw(tbl)} WHERE user_id = ${userId}``

H-6: Admin bootstrap endpoint has no CSRF protection

File: server/routes/admin.ts

router.post("/bootstrap", writeLimiter, async (req, res) => {

The /api/admin/bootstrap endpoint has no requireAdmin middleware and no CSRF protection. While it correctly checks adminCount === 0 before granting, a CSRF attack on a freshly-deployed instance (before any admin exists) could grant admin to an attacker's account if they can trick a logged-in user into visiting a malicious page.

Fix: Add csrfProtection to the bootstrap endpoint.

H-7: WebsiteContent logout uses wrong endpoint

File: client/src/App.tsx, WebsiteContent.handleLogout():

await fetch("/auth/logout", { method: "POST", credentials: "include" });

The actual logout endpoint registered in server/auth/google.ts is POST /auth/logout (not /api/auth/logout). Looking at the server code this is actually correct — the route is /auth/logout. However performFullLogout() in authClient.ts calls ${AUTH_DOMAIN}/api/auth/logout, which does not exist as a registered route. The registered route is /auth/logout (no /api prefix). This means the Electron/JWT auth path logout always hits a 404, and the session is never actually invalidated on the server — only the local store is cleared.

Impact: Server-side session cookie persists after logout in Electron mode. The user appears logged out locally but the session cookie remains valid until natural expiration (7 days).

Fix: Change performFullLogout in authClient.ts to call /auth/logout instead of /api/auth/logout.

M-5: stripeWebhookEvents table records events before idempotency check

File: server/webhookHandlers.ts:

// Persist every webhook event for admin visibility (async, non-blocking)
try {
  await storage.addStripeWebhookEvent({ ... });
} catch (err) { ... }

switch (event.type) {
  case 'checkout.session.completed':
    await handleCheckoutCompleted(event); // idempotency check inside here

The event is stored in stripeWebhookEvents before the idempotency check in handleCheckoutCompleted. This means duplicate webhook deliveries will always add a record to stripeWebhookEvents even when correctly deduplicated. The admin Stripe events panel will show duplicates, which could mislead operators into thinking an event was processed twice.

Fix: Move the addStripeWebhookEvent call into handleCheckoutCompleted after the idempotency check passes, or add a note in the admin panel that the events table records all deliveries, not all processings.

M-6: deleteUser SQL transaction — sessions table query uses JSONB path that may miss records

File: server/storage.ts:

await tx.execute(drizzleSql`
  DELETE FROM sessions
  WHERE (sess->>'userId') = ${userId}
     OR (sess->'passport'->>'user') = ${userId}
`);

Passport serializes the user as an ID string (passport.serializeUser returns user.id), so the session JSON structure is { passport: { user: "uuid-here" } }. The second path sess->'passport'->>'user' correctly handles this. But the first path sess->>'userId' would only match sessions where a top-level userId key exists, which Passport sessions don't have. This is dead code — the delete only works via the second path. Not a security issue (the correct path works) but worth cleaning up.

M-7: retryRefreshEntitlements type signature mismatch

File: client/src/App.tsx line:

const result = await retryRefreshEntitlements({
  attempts: 8,
  delayMs: 500,       // ← this parameter does not exist
  initialDelayMs: 500,
});

The retryRefreshEntitlements function signature in authClient.ts accepts { attempts?, initialDelayMs?, baseDelayMs? } — the field is baseDelayMs, not delayMs. The delayMs: 500 key is silently ignored. The effective base delay is the default 400ms. Not a security issue but the retry timing is not what the caller intends.

M-8: Admin CSV export exposes all user data without rate limiting for large datasets

The export endpoint uses a 10,000 row limit, includes Stripe customer IDs, email addresses, device IDs, and all plan details. It's correctly admin-gated, but there's no audit log entry when an export is performed. An admin who exports the full user database leaves no trace in adminLogs.

Fix: Add an audit log entry for CSV exports.

File: client/src/pages/Admin.tsx:

getState() is a Zustand escape hatch that bypasses React's subscription mechanism. This works correctly but means the headers function always uses the JWT at call time. If the JWT is refreshed mid-session, the new token is used correctly (since getState() reads the current state).
