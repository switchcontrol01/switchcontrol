TASK
Refactor SwitchControl’s Windows privilege model to use startup elevation as the primary admin flow, while preserving a limited non-admin mode and adding real post-apply verification for tweaks.

PROBLEM
The current tweak flow relies on per-action elevation prompts and produces poor UX:
- repeated UAC interruptions
- inconsistent success/failure behavior
- toggles can appear enabled even when the backend action was blocked
- “Elevation Failed” is too vague and not premium
- admin state is not treated as a first-class app capability

This app is a system-level optimizer. Admin capability should be determined at startup, not awkwardly during every protected action.

GOAL
Implement a launch-time admin model with these exact behaviors:

1. On app startup, detect whether the Electron process is elevated.
2. If not elevated, the app must still open, but in LIMITED MODE.
3. Show a premium startup/admin gate that explains:
   - admin unlocks full tweak execution
   - user may continue in limited mode
   - or restart the app as administrator
4. Add a backend IPC method that relaunches the app with elevation and exits the current instance.
5. Protected tweaks must not trigger their own UAC prompt anymore if the app is already elevated.
6. Protected tweaks must be blocked cleanly in limited mode with exact UI feedback.
7. After every tweak apply attempt, verify the real system state before updating the UI.
8. The toggle UI must reflect VERIFIED STATE ONLY, never assumed state.
9. Keep the app fluid and premium. No ugly native-feeling dead ends.

IMPLEMENTATION

A. ADD GLOBAL ADMIN STATE
Create a single source of truth for app privilege state.

Backend:
- Add an IPC handler like `app:isElevated`
- Return a boolean based on actual Windows admin/elevation status
- Add logging for startup privilege detection

Frontend:
- Add a global privilege store or app-level state:
  - `isElevated`
  - `adminModeKnown`
  - `isLimitedMode`
- Resolve this once on app boot
- Make it available to Tweaks, Power Plan, BIOS Advisor lock decisions if needed, and premium/admin CTA components

B. STARTUP ADMIN GATE
Create a branded admin gate/modal shown on launch if not elevated.

Requirements:
- Must match SwitchControl visual language
- Must not feel like a generic OS warning
- Copy should be direct and premium
- Buttons:
  1. “Restart as Administrator”
  2. “Continue in Limited Mode”

Behavior:
- If “Restart as Administrator” is clicked:
  - call backend IPC to relaunch elevated
  - current instance exits
- If “Continue in Limited Mode”:
  - app continues normally
  - protected areas stay visible but clearly limited

C. RELAUNCH ELEVATED
Backend must support restarting the app as admin.

Implement a safe Electron relaunch path on Windows:
- relaunch the current executable with elevation
- preserve packaged app behavior
- exit the current instance after spawning elevated instance
- add robust logging
- handle refusal/cancel cleanly

Need:
- no broken path quoting
- no temp-file hacks if not needed
- make it robust in packaged Electron, not just dev

D. REMOVE PER-ACTION UAC AS PRIMARY FLOW
Refactor tweak execution so it no longer depends on per-action admin prompts when startup elevation already exists.

Rules:
- If app is elevated:
  - protected tweaks run directly
  - no UAC prompt
- If app is not elevated:
  - protected tweaks DO NOT attempt apply
  - instead return a structured failure:
    - `reason: "requires_admin"`
    - `message: "This tweak requires administrator mode."`

Do not leave old mixed logic in place where some actions still try to elevate mid-flow unless absolutely required for special edge cases.

E. TWEAK VERIFICATION LAYER
This is mandatory.

For every tweak:
1. apply backend change
2. re-read actual system state from source of truth
3. compare expected vs actual
4. only then update UI

Add per-tweak verification support:
- registry-based tweaks: re-read registry
- service tweaks: re-read service status/start type
- power plan tweaks: verify active scheme and underlying values where possible
- network tweaks: verify adapter/property state where possible

Response shape should include:
- `attempted`
- `verified`
- `actualState`
- `expectedState`
- `failureReason`
- `userMessage`

F. UI STATE MUST BE VERIFIED ONLY
Tweak cards must use real verified state, not optimistic state.

If apply fails:
- toggle animates back
- card briefly shows failed status
- clear reason shown inline or toast
- examples:
  - “Requires administrator mode”
  - “Blocked by Windows policy”
  - “Verification failed: setting did not change”
  - “Unsupported on this system”

Do not keep vague “Elevation Failed” as the main message.

G. TWEAK CARD CLEANUP
Clean up the tweak cards while in free/limited mode:
- free-member unlock CTA must stay inside its section bounds
- remove unnecessary visual clutter such as the extra “real” badge/icon where it adds noise
- premium state can stay richer
- free state should be cleaner and less bloated

H. LOGGING
Add clean scoped logs:
- `[AdminBoot]` privilege detection
- `[AdminRelaunch]` relaunch attempt/result
- `[TweakApply]` tweak id, requested state, admin state
- `[TweakVerify]` expected vs actual
- `[TweakUI]` limited mode block / rollback / verified success

CHECKLIST
- Detect admin/elevated mode on startup
- Add polished admin startup gate
- Implement relaunch-as-admin flow
- Support limited mode without crashing app
- Remove repeated per-action UAC prompt dependency
- Protected tweaks blocked cleanly in limited mode
- All tweak toggles driven by verified state only
- Failed tweak attempts roll back visually
- Exact failure reasons surfaced
- Free-mode CTA stays inside layout bounds
- Unnecessary tweak badge clutter reduced
- Logs added for boot, relaunch, apply, verify

FINAL OUTPUT
Return:
1. files changed
2. exact admin detection method used
3. exact relaunch method used
4. protected tweak flow before vs after
5. verification strategy used per tweak type
6. any edge cases or remaining limitations
