TASK

Find exactly why SwitchControl can hit extremely high CPU usage, including reports of 100% CPU while the app is open.

PROBLEM

Multiple users are reporting that the app itself causes very high CPU usage. This is unacceptable for an optimization app.

From current evidence, I already suspect:

- duplicate telemetry subscriptions
- repeated intervals
- render loops
- dashboard rerender storms
- excessive console logging
- tweak intelligence recalculating too often
- live graph updates running too frequently
- heavy animation/repaint cost from glass/blur/glow effects

GOAL

Make idle and dashboard CPU usage low and stable.
The app must not hammer CPU just by being open.

REQUIRED INVESTIGATION

1. Audit all telemetry startup paths

- find every place telemetry starts
- ensure only one manager/interval/subscription can run at once
- ensure all listeners and intervals are cleaned up on unmount
- explain why logs currently show things like “Telemetry Manager already running” and repeated “subscription resumed”

2. Audit all high-frequency logs

- remove or gate all spam logging in production
- especially telemetry, disk graph, premium truth, auth context, dashboard live state
- no repeated console logging inside active loops

3. Audit dashboard render frequency

- measure what rerenders on each telemetry tick
- identify components rerendering too often
- memoize where needed
- split state so one telemetry update does not rerender the whole dashboard

4. Audit graph update frequency

- reduce sampling/update frequency to something sane
- ensure history arrays are bounded
- avoid unnecessary object recreation each tick
- avoid repeated disk object logs and repeated graph pipeline churn

5. Audit tweak intelligence and premium/auth checks

- these must not recompute continuously on every live tick unless truly needed
- premium/auth validation must not loop in background
- intelligence ranking should be throttled/debounced and not tied to every tiny telemetry update

6. Audit visual paint cost

- check whether blur/glass/glow/animated gradients/charts are causing excessive repaint cost
- disable or reduce expensive effects where needed in live dashboard paths
- prioritize smoothness and low CPU over decorative effects

7. Production behavior

- ensure development-only diagnostics are removed or gated
- packaged app must not run debug/dev loops
- verify CPU usage in packaged production build, not only Replit/dev mode

OUTPUT REQUIRED

Return:

1. exact root cause or causes
2. exact files responsible
3. exact loops/subscriptions/intervals found
4. exact logs removed
5. exact throttling/debounce/memoization changes made
6. before vs after CPU usage results
7. confirmation only one telemetry manager/subscription can exist at a time
8. confirmation dashboard no longer causes high CPU at idle
