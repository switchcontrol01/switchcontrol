Part A: Sensors helper is either real or fake

Replit created the C# project, but that does NOT mean the installer contains a working SensorsHelper.exe.

In Replit shell (or wherever the repo builds), run this exact sequence:

1. Build the helper:



cd electron/sensors-helper
dotnet publish -c Release -r win-x64 --self-contained false -p:PublishSingleFile=true -o ../bin

2. Confirm the file exists:



ls -la ../bin

You must see:

electron/bin/SensorsHelper.exe


If you do not see it, the installer cannot possibly have it.

A2) Confirm electron-builder includes it

Open electron-builder.json and confirm you have something like:

extraResources includes the helper, for example:


"extraResources": [
  {
    "from": "electron/bin/SensorsHelper.exe",
    "to": "bin/SensorsHelper.exe"
  }
]

If it is not in extraResources, the EXE will not ship.

A3) Confirm the app can actually run it

In Electron main process code, the path must be different in dev vs prod.

Your code must resolve like this:

Dev: path.join(app.getAppPath(), "electron/bin/SensorsHelper.exe") or similar

Prod: path.join(process.resourcesPath, "bin/SensorsHelper.exe")


If they always reference electron/bin/... it will work in dev and fail in installer.

This is the most common “it works for me” trap.

Part B: Security changes can quietly break app actions

CSRF is the main landmine. OAuth and /api/auth/exchange must NOT require CSRF.

B1) Confirm CSRF is NOT applied to these routes

Open server/routes.ts and server/index.ts and confirm CSRF middleware is NOT used on:

GET /api/auth/google

GET /api/auth/google/callback

GET /api/auth/discord

GET /api/auth/discord/callback

POST /api/auth/exchange

GET /api/me


If any of those are behind CSRF, your login will randomly fail or your session will never stick.

B2) Confirm there is a CSRF token endpoint

They mentioned adding one. Verify you have something like:

GET /api/csrf returns { csrfToken: "..." }

and sets the CSRF cookie


If this endpoint does not exist, the frontend cannot ever send CSRF properly.

B3) Confirm frontend sends CSRF token ONLY where needed

Your frontend should do this pattern:

1. On app start (or before first write request):



GET /api/csrf with credentials: "include"

store csrfToken


2. For write endpoints only:



add header X-CSRF-Token: <token>

still use credentials: "include"


Write endpoints include:

PATCH /api/settings

POST /api/tweaks/*

POST /api/ai-scan

POST /api/clear-ram

POST/DELETE /api/history


If they added CSRF headers to everything, that is sloppy but usually not fatal. If they added CSRF protection to read endpoints, that is fatal.

Expected:

If this fails, CSRF will break every write endpoint.

C3) Write endpoint test

Still in browser devtools console, run:

await fetch("/api/clear-ram", {
  method: "POST",
  credentials: "include",

Expected:

200 response body If you get 403, CSRF is active but your client is not sending token correctly.
