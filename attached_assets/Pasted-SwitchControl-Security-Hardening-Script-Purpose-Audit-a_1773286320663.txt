SwitchControl Security Hardening Script

Purpose
Audit and harden the SwitchControl website backend and Electron desktop application before public release.

Every item must be evaluated and marked PASS or FAIL with evidence.

Do not mark PASS without proof.

---

SECTION 0 — BASELINE RULES

These rules apply everywhere.

[CRITICAL]

No secrets in frontend bundles, preload scripts, renderer code, or packaged Electron builds.

Proof:
Search compiled client output and Electron asar for:

API keys
Stripe secrets
OAuth secrets
JWT secrets
Database URLs

Result must show none present.

---

All environment secrets stored only in server environment variables.

Proof:
.env not committed to repository
.env not bundled in build output
Server logs do not print secret values.

---

Structured logging enabled.

Every request log must contain:

requestId
timestamp
endpoint
status code

Proof:
Show example logs from server.

SECTION 1 — AUTHENTICATION AND SESSION SECURITY

[CRITICAL]

JWT signing secret must be strong.

Requirements:

Minimum 32 bytes
Loaded from environment variable
No default fallback value
Not committed in repository

Proof:
Show server config reading secret from environment.

---

JWT validation must enforce:

Signature validation
Expiration check
Algorithm verification (reject alg=none)
Optional issuer and audience checks if configured

Proof:
Add unit tests that reject:

tampered token
expired token
token with invalid algorithm

---

Session cookies must use secure flags if cookies are used.

Required flags:

HttpOnly
Secure
SameSite=Lax or SameSite=Strict

SameSite=None only allowed if Secure flag present.

Proof:
Verify cookie flags in browser DevTools.

---

OAuth callback handler must validate state parameter.

Proof:
Force state mismatch and confirm login fails.

---

Logout must invalidate session.

Proof:
After logout call /api/me and confirm loggedIn = false.

---

[CRITICAL]

SECTION 18 — ERROR HANDLING AND FAIL-SAFE BEHAVIOR

[CRITICAL]

Security failures must fail closed.

Rules:

If authentication validation fails → request denied
If entitlement check fails → premium access denied
If IPC validation fails → handler rejects request safely
If token parsing fails → session treated as unauthenticated

Proof:
Demonstrate failure scenarios for each case.


---

Unexpected runtime errors must not expose sensitive data or crash the application.

Proof:
Simulate malformed requests and confirm safe handling.
