TASK
Harden Stripe premium confirmation, entitlement retry, deep-link validation, and premium status routes.

PROBLEM
The payment flow mostly works, but there are security and reliability gaps:
- /api/stripe/confirm may grant premium without authentication
- /api/stripe/confirm has no rate limit
- success page may open the app before premium is confirmed
- retryRefreshEntitlements can stack repeated /api/me calls
- expired JWT can be cleared on network failure
- deep links are passed to renderer without validation
- /api/user/premium-status is unauthenticated or redundant

GOAL
Make premium activation secure, reliable, and hard to abuse. Payment confirmation must never trust checkoutUserId or session_id alone.

IMPLEMENTATION

1. Lock down /api/stripe/confirm

Find:
app.post("/api/stripe/confirm", ...)

Change it so it requires authenticated user identity before doing any premium update.

Accepted auth sources:
- verified Passport session user
- verified Bearer JWT user through requireJwt

Do not allow unauthenticated access.

Hard rule:
If no authenticated user exists, return:

401
{ ok: false, error: "Authentication required" }

Also verify:
- Stripe checkout session exists
- payment_status is "paid"
- session mode is "payment"
- metadata.userId exists
- metadata.userId matches authenticated user id
- line item price id matches STRIPE_PREMIUM_PRICE_ID

Only then allow:
storage.setUserPlan(authenticatedUser.id, "premium")

Do not use checkoutUserId from body as truth.

2. Add rate limit to /api/stripe/confirm

Add a simple in-memory limiter if no shared limiter exists.

Limit by:
- IP
- session_id

Max:
5 attempts per minute

Return:
429
{ ok: false, error: "Too many attempts" }

This must happen before Stripe API calls to avoid spam.

3. Success page must wait for premium confirmation

On payment success page:
- call /api/stripe/confirm
- wait until confirm returns premium/isPremium true
- only then show or enable “Open App”

If confirm is still pending:
show:
“Verifying your premium purchase…”

If confirm fails because webhook is still delayed:
retry with gentle backoff for up to 60 seconds.

Do not open Electron immediately before premium is confirmed.

4. Add singleton guard to retryRefreshEntitlements

In retryRefreshEntitlements:

Add module-level guard:

let retryRefreshEntitlementsInFlight: Promise<any> | null = null;

If already running:
return the existing promise

When complete:
clear the guard in finally

This prevents multiple components/deep-link handlers from stacking /api/me calls.

5. Do not clear JWT on network failure

In safeGetJwt/apiFetch/reissue logic:

If JWT is expired:
- attempt reissue
- if reissue succeeds, use fresh JWT
- if reissue fails because of network/server error, keep old JWT stored
- only clear JWT if cloud clearly returns 401/invalid token/session invalid

Do not log users out just because network failed.

6. Validate deep link before renderer

In electron/main.js deliverDeepLink(url):

Before sending auth-callback IPC:

Reject if:
- url is not a string
- url does not start with "switchcontrol://"
- url length > 2048
- URL cannot be parsed
- hostname/path is not an allowed auth route

Allowed examples:
switchcontrol://auth/callback
switchcontrol://auth/success
switchcontrol://premium/activated

If invalid:
log:
[DeepLink] rejected reason=...

Do not send invalid URLs to renderer.
