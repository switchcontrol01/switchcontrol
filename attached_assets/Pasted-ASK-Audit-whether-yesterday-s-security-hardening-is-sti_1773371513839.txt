ASK: Audit whether yesterday’s security hardening is still interfering with Electron login flow

PROBLEM

Electron login still does not work.

We previously applied a security checklist yesterday that changed multiple parts of the app, and it is possible that one or more of those hardening changes are still interfering with the Electron login return path.

Important context:
- website auth behavior has already been worked on separately
- the remaining issue is Electron login not completing properly
- browser auth may succeed, but the app still does not become logged in
- custom protocol handoff / success-page return path may still be blocked or degraded by security-related changes

GOAL

Determine whether any security hardening changes from yesterday are still interfering with the Electron login flow.

Do not guess.
Audit the actual Electron login path end-to-end and identify whether any security rule, CSP, navigation protection, redirect restriction, cookie rule, protocol restriction, or renderer/main-process security behavior is blocking completion.

IMPLEMENTATION

SECTION 1 — AUDIT ONLY THE ELECTRON LOGIN PATH

Inspect the Electron login flow specifically:

Electron app
→ open system browser
→ Google auth
→ backend callback
→ success/handoff page
→ custom protocol launch
→ Electron deep link receipt
→ callback forwarded to renderer
→ token/code exchange
→ authenticated state commit

Do not re-audit unrelated website auth logic unless it directly affects this path.

SECTION 2 — REVIEW YESTERDAY’S SECURITY CHANGES AGAINST THIS FLOW

Audit all recent hardening that could interfere with Electron auth, including:

- Helmet / CSP
- scriptSrc
- navigation restrictions
- redirect restrictions
- custom protocol launch restrictions
- frame / referrer policies if relevant
- cookie settings relevant to Electron exchange
- CSRF behavior on exchange route
- CORS behavior for Electron exchange requests
- auth route middleware
- protocol handling guards
- renderer security changes
- preload / IPC restrictions
- URL validation / sanitization
- allowlists for destinations or origins

SECTION 3 — IDENTIFY EXACT SECURITY REGRESSION IF PRESENT

Determine whether the remaining Electron issue is caused by one of the following:

A. success page script is still blocked or degraded  
B. browser custom protocol launch is blocked by a security change  
C. Electron callback/exchange request is blocked by CORS/CSRF/security middleware  
D. URL validation/allowlist logic is rejecting the callback path  
E. protocol handling was weakened or broken by security-related code  
F. no remaining security issue exists and the problem is elsewhere

Report the exact answer, not a broad guess.

SECTION 4 — VERIFY EXCHANGE ROUTE COMPATIBILITY

Audit the Electron exchange path:

POST /api/auth/exchange

Confirm that security hardening is not blocking it through:
- CORS
- CSRF
- header validation
- cookie/session restrictions
- JWT or auth middleware misapplication

SECTION 5 — VERIFY SUCCESS PAGE AND CUSTOM PROTOCOL LAUNCH

Confirm whether the browser success page is still capable of launching:

switchcontrol://...

Check for any security changes that interfere with:
- inline/external script execution
- navigation to custom protocols
- redirect restrictions
- URL sanitization

SECTION 6 — KEEP VALID SECURITY HARDENING

Do not broadly remove security protections.

If a breaking security rule is found:
- identify it precisely
- relax only what is necessary for Electron auth compatibility
- keep the rest of the hardening intact

CHECKLIST

[ ] Exact security interference was identified or ruled out

FINAL OUTPUT

After auditing, report:

- whether any security checklist change is still interfering with Electron login
- exact file(s) involved
- exact rule or protection causing interference, if any
- whether the issue is CSP, redirect behavior, CORS/CSRF, protocol handling, or something else
- what minimal change is required to restore Electron login
- what security hardening remains safely in place
