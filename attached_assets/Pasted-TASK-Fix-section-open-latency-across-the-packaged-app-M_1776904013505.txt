TASK
Fix section-open latency across the packaged app. Many users report that opening sections takes around 4 seconds. The UI must feel instant when navigating between sections.

PROBLEM
Right now page navigation is too heavy. When users click sections, pages appear to block while mount-time effects run backend calls, auth checks, registry reads, PowerShell/system scans, and other expensive work.

Observed issues:
- section click can take ~4s before usable UI appears
- some users get startup/section exceptions like "registry key not found after write"
- backend logs still show invalid JWT spam during normal app usage
- trust is damaged because the app feels heavy and unstable

GOAL
Make page navigation feel immediate:
- section shell renders instantly
- cached/last-known data appears first
- expensive backend/system work happens after render, in background, or only on explicit user action
- no mount-time registry writes or privileged operations unless the user clicked Apply / Run / Scan
- no invalid auth spam during normal page navigation
- no unnecessary duplicate fetches on mount

FILES TO AUDIT
- all page components in client/src/pages/
- all section-specific hooks in client/src/hooks/
- any shared data hooks used on section mount
- App.tsx
- AppLayout.tsx
- query client / fetch wrappers
- requireCloudAuth related callers
- routes used by Security, Focus Mode, Network Tweaks, App Booster, Startup Apps, Cleaner

HARD REQUIREMENTS

1. INSTANT PAGE SHELL RENDER
- Every page must render its layout, title, cards, placeholders, and cached values immediately.
- Do not block initial render on backend/system calls.
- Replace hard loading gates with skeletons or stale cached data.

2. REMOVE HEAVY MOUNT-TIME WORK
- Audit every useEffect on page mount.
- Categorize each effect:
  A. safe lightweight fetch
  B. cached fetch
  C. expensive system inspection
  D. write/mutate operation
- C and D must NOT run automatically on page open unless absolutely required.
- Registry writes, PowerShell writes, tweak verification writes, scan launches, cleaner actions, startup edits, and similar must only run from explicit user action.

3. DEFER EXPENSIVE CALLS
- Expensive calls must be delayed until after first paint.
- Use one of:
  - requestIdleCallback with timeout fallback
  - setTimeout after initial render
  - explicit "Refresh / Scan / Detect" button
- If a section needs live data, load cached state first, then refresh in background.

4. CACHE FIRST
- For every section endpoint that returns mostly stable data, use cached last-known response first.
- Use React Query correctly:
  - sensible staleTime
  - keepPreviousData where appropriate
  - avoid immediate refetch on remount if data is fresh
- Do not refetch the same section data repeatedly when switching tabs quickly.

5. FIX AUTH SPAM
- Find why protected routes are still being called with invalid JWTs during normal navigation.
- Ensure pages/hooks do not call protected endpoints until auth state is actually ready and valid.
- If token is invalid, fail once, clear bad auth state, and stop retry spam.
- No repeated invalid-signature log bursts during normal UI navigation.

6. ELIMINATE DUPLICATE CALLS
- Add temporary instrumentation per route and per page mount:
  - page mounted
  - fetch started
  - fetch completed
  - expensive scan started
- Use this to identify duplicate calls on one click.
- Remove duplicate useEffects, duplicate polling, duplicate scans, duplicate auth-dependent calls.

7. NO WRITE ON OPEN
- Confirm that section open never triggers:
  - registry writes
  - PowerShell writes
  - tweak apply/revert
  - startup changes
  - cleaner deletions
  - focus mode writes
- If any do, move them behind explicit buttons only.

8. EXCEPTION HARDENING
- Any "registry key not found after write" or similar backend/system exception must:
  - not appear just from opening the page
  - be caught and surfaced cleanly
  - not break page rendering
- Reads must tolerate missing keys.
- Writes must verify existence and expected path before assuming success.

9. MEASURE AND REPORT
Add timing logs around each section-open path:
- click timestamp
- first React render
- first meaningful paint of page shell
- first backend fetch complete
- expensive scan complete
Return a report like:
- Home: shell 80ms, data 220ms
- Security: shell 95ms, advanced scan deferred, first live data 300ms
- Network: shell 90ms, state fetch 180ms
- Focus: shell 85ms, history deferred until auth ready
- App Booster: shell 100ms, game scan deferred/manual
Target:
- shell visible under 150ms
- page usable under 300ms
- expensive scans only after render or on manual action
