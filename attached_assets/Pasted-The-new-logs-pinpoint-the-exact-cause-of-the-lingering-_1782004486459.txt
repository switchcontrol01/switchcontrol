## What Is Happening Under the Hood?
The systeminformation library (or your native WMI script wrapper) is spawning a massive queue of WMI query tasks (gwmi / Get-CimInstance). On Windows, the WMI Repository Subsystem (wmiprvse.exe) runs on a shared system core.
When 11 heavy hardware queries are thrown at it simultaneously, the WMI service spikes your processor to 100%, encounters thread lockouts, and blocks. This massive background thrashing chokes out your system's real-time audio driver channels, causing severe audio crackling and glitches.

You need to optimize electron/main.js (or wherever your SysIntelligence engine is initialized) to modify how it probes hardware on startup:
## 1. Disable the Unnecessary "Deep" Probes
You do not need deep motherboard component analysis or disk layout telemetry just to draw an app interface. Turn off the probes that are timing out.
Inside your backend config or SysIntelligence setup, disable the high-latency options:

// ❌ OLD WAY: Fires everything, freezing the system coreconst data = await si.get({
  bios: '*',
  baseboard: '*',
  cpu: '*',
  graphics: '*',

  memLayout: '*'

//  FIXED WAY: Only fetch what the app actually displays. Bypass the broken probes.const data = await si.get({

## 2. Kill the 11-Process Parallel Burst (Enforce Sequential Backoff)
Instead of launching all deep collection probes concurrently, modify your Background deep collection trigger to space out its tasks. If you must have the data, query them with a step delay:

// electron/main.js - Stagger deep background metrics safely
setTimeout(async () => {
  console.log("[SysIntelligence] Step 1: Querying Memory...");
  await si.mem();
  
  setTimeout(async () => {
    console.log("[SysIntelligence] Step 2: Querying Graphics...");
    await si.graphics();
  }, 3000); // 3-second recovery window for the Windows WMI stream
}, 15000); // Delayed safely away from initial app launch window

## 3. Run a Clean WMI Re-Index on Your Development PC
Because every single probe timed out (MB=null, BIOS=null, GPUs=0), your own computer's local Windows WMI registry repository might be corrupt, forcing the helper engine to wait for entries that cannot be read.
Run this script in an Administrative PowerShell window to clean and rebuild your PC's WMI engine:
