TASK
Redesign and fully implement the Startup Apps page with FULL FRONTEND AND FULL BACKEND so it becomes a premium startup orchestration system instead of a repetitive toggle/checklist page.

GOAL
Turn Startup Apps into a real, product-grade startup control center that:
- actually reads startup apps from the system
- actually enables / disables / delays startup items through the backend
- actually supports startup profiles
- uses the timeline as a core premium feature
- removes the current over-reliance on repetitive “tick / enable” style row UI
- feels fluid, intentional, animated, and expensive

CRITICAL
Backend is mandatory.
Do NOT come back with mostly visual polish.
Do NOT leave startup actions simulated.
Do NOT fake delay / disable / enable state.
Do NOT hardcode boot impact numbers without logic behind them.
Do NOT keep the current repetitive checkbox/toggle-heavy row interaction model as the primary UX.

If an action is shown in the UI:
- it must work through the backend
- it must return real state
- it must be verifiable where possible

IMPORTANT
The “Show Timeline” concept is strong and should be kept and upgraded.
Use it as a core part of the redesign.

Keep the SwitchControl design language:
- matte dark base
- purple/pink primary accents
- cyan secondary accents
- premium glass cards
- strong hierarchy
- fluid motion
- clean graph/timeline visuals
- no clutter
- no generic admin dashboard feel

PROBLEM
The current Startup Apps page has a good idea, but the interaction model is weak.

Current likely issues:
- too many repetitive row-level enable/tick interactions
- page feels like a checklist instead of a startup orchestration system
- timeline is unique but under-leveraged
- startup data/state may be simulated or partially wired
- delay/disable logic may not really work
- boot impact may be hardcoded
- row design feels repetitive and lower-value than the concept deserves

We need to fix:
1. backend functionality
2. page interaction model
3. layout hierarchy
4. premium graph/timeline UI
5. honest startup state

IMPLEMENTATION

1. FULL STARTUP APPS BACKEND AUDIT
Audit the current Startup Apps implementation.

Check:
- how startup apps are discovered
- whether startup entries come from real system sources
- whether enable/disable works
- whether delay actually works
- whether profiles work
- whether timeline is real or simulated
- whether startup categories are backend-driven
- whether impact values are real or hardcoded
- Electron/main/preload/IPC/backend routes
- verification logic
- persistence of delayed/disabled states

Identify:
- what is real
- what is simulated
- what is partially wired
- what is fake
- what needs full backend implementation

2. CREATE / FIX REAL STARTUP ENGINE
Implement a real backend startup engine.

Suggested structure:
- startup-engine.ts
- startup-scan-service.ts
- startup-profile-registry.ts
- startup-execution-service.ts
- startup-delay-service.ts
- startup-verification-service.ts

This system must support:
- scanning startup items from real Windows startup sources
- enabling/disabling startup items
- delaying startup items
- grouping startup items
- generating timeline state
- verifying resulting state
- returning structured frontend data

3. REAL STARTUP ITEM DISCOVERY
Read startup items from real system sources where appropriate, such as:
- Registry Run keys
- Startup folders
- Task Scheduler entries where relevant
- common startup-enabled app sources

Each startup item should include:
- id
- name
- publisher
- category
- enabled/disabled state
- estimated startup impact
- delay state
- launch source
- whether it is safe to disable
- whether it is system-critical / should be protected

Do NOT fake discovered items.
