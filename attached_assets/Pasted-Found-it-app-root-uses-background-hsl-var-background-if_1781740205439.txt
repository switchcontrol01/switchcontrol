Here's exactly what was wrong and what I did:

The actual root cause: backgroundColor: '#07090D' sets the DWM native surface to dark, but on Windows it cannot prevent the one-frame white compositor init frame that appears when a frameless window first becomes visible. This is a known Windows/Electron quirk — the DWM briefly shows its own uninitialized frame before Chromium's renderer takes over.

The fix — two things:

1. transparent: true + setOpacity(0→1) in main.js

transparent: true         ← enables setOpacity() on Windows (no-op without this)
backgroundColor: '#00000000'  ← required companion

Then in _tryShowWindow():

mainWindow.setOpacity(0)   // OS-level invisible
mainWindow.show()
mainWindow.focus()
mainWindow.setOpacity(1)   // reveals already-painted dark Splash

All three are synchronous native calls in the same JS tick. The DWM gets one composite — at opacity:1 — so the first frame the user ever sees is the dark Splash. There is no moment where white can appear.

2. Reverted CameraGlow
The always-rendered filter:blur div from last session was wrong — it runs the blur shader every single frame with no content (pure waste), adds compositor complexity during startup, and didn't actually address the DWM issue (which is native OS-level, not a GPU layer problem).
