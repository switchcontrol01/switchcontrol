TASK: Fix AI Advisor / BIOS Advisor "Failed to fetch" in packaged Electron by removing stale API base fallback, hardening CSRF bootstrap, and cleaning Electron cookie inconsistency

PROBLEM

AI Advisor and BIOS Advisor are still showing "Failed to fetch" even though the OpenAI API key exists and the backend routes themselves appear functional.

From the current codebase, the strongest root cause is NOT the OpenAI key. The failure is most likely happening between the Electron renderer and the embedded backend.

Exact issues found:

1. API base resolution in packaged Electron is flawed
- the embedded backend now runs on a dynamic free port from backend-launcher.js
- client/src/lib/api.ts still falls back to hardcoded http://127.0.0.1:5000/api
- worse, that fallback gets cached permanently in _resolvedApiBase
- so if getBackendPort() returns null even once during startup timing, the renderer can permanently talk to the wrong port for that session
- that produces real network failure and browser/Electron fetch throws "Failed to fetch"

2. CSRF bootstrap is too weak and hides failures
- ensureCsrfToken() catches fetch errors and silently returns empty string
- that means the real bootstrap failure gets masked
- then POST requests proceed without a valid CSRF header
- that creates misleading downstream failures and makes debugging worse

3. Electron auth cookie handling is still inconsistent in one route
- server/auth/google.ts still hardcodes secure: true and sameSite: "none" for auth_source and auth_next cookies
- that is web-style behavior, not packaged Electron localhost behavior
- this is not necessarily the direct AI/Bios fetch bug, but it shows the Electron vs web cookie split is still not fully centralized and can cause more instability later

4. Abort logic in AI Advisor is incomplete
- AiAdvisor creates an AbortController
- but apiPost/apiFetch do not receive the signal
- so requests are not actually aborted
- this is not the main root cause of Failed to fetch, but it is sloppy and should be fixed while touching this area

GOAL

Make packaged Electron API calls bulletproof.

Required result:
- the renderer must always resolve the real embedded backend port before making API calls
- no permanent fallback to dead port 5000 just because backend port was not ready on first lookup
- CSRF bootstrap must fail loudly and clearly when broken
- Electron auth cookie behavior must be aligned with packaged localhost mode
- AI Advisor and BIOS Advisor must stop failing because of bad renderer to backend transport
- request cancellation must actually work where abort controllers are being used

SECTION 1 — FIX ELECTRON API BASE RESOLUTION IN client/src/lib/api.ts

Audit and replace the packaged Electron API base logic.

Current bug:
- resolveApiBase() tries electronAPI.getBackendPort()
- if null, it falls back to 127.0.0.1:5000
- then caches that wrong value forever

This is unacceptable because backend-launcher.js now uses dynamic free port allocation.

Required behavior:
- do NOT permanently cache a fake fallback port if backend port is not ready yet
- add a proper async wait/retry path for Electron packaged mode
- only cache the resolved API base after a valid backend port is returned
- if backend port never becomes available within a sane timeout, throw a real error instead of silently using 5000
- remove the fake synchronous assumptions around file:// packaged mode

Implement something like this:

- keep _resolvedApiBase cache
- add _resolvingApiBase promise dedupe
- for Electron:
  - try getBackendPort() repeatedly for a short startup window
  - only accept a real numeric port
  - then cache http://127.0.0.1:${port}/api
- if no port is available after retries, throw a hard error:
  "Embedded backend port was not available in time"

Important:
- do NOT keep the current permanent hardcoded fallback to 5000 in packaged Electron
- if you keep 5000 anywhere, it must only be for explicitly known dev mode behavior, not for packaged dynamic-port mode

SECTION 2 — HARDEN CSRF BOOTSTRAP IN client/src/lib/api.ts

Current problem:
- ensureCsrfToken() swallows errors and returns empty string
- this hides the real issue and lets POST requests continue in a broken state

Required changes:
- ensureCsrfToken() must:
  - check existing cookie first
  - if missing, fetch /csrf-token using resolved API base
  - if fetch fails or response is not ok, throw a real error
  - if token is missing from response, throw a real error
- do NOT silently return empty string on failure

Goal:
- if CSRF bootstrap is broken, the UI should surface a real transport/bootstrap failure
- do not let the app fake progress with invalid security state
