TASK
Fix the frontend state bug where tweaks visually appear reverted or greyed out after switching tabs, changing sections, reopening the app, or returning later, even though the backend still shows them as verified and applied.

PROBLEM
Real users are reporting this exact behavior:
- apply a tweak
- switch to another tab or section
- come back later
- tweak looks visually off / grey / reverted
- but backend verification says it is still applied

So the actual tweak state and the rendered UI state are diverging.

This is a trust-killer.
The app looks broken even when the backend is correct.

GOAL
Make tweak cards always reflect the real canonical state.

If a tweak is applied and verified, it must stay visually applied:
- after tab switches
- after route changes
- after remounts
- after app relaunch
- after background refreshes
- after async rechecks

The UI must never paint stale false/off state over a verified true/applied state.

ROOT ISSUE TO FIND
This is almost certainly one of these:

1. LOCAL UI STATE IS CANONICAL WHEN IT SHOULD NOT BE
A component is storing:
- isEnabled
- selectedOption
- sliderValue
- pendingValue
locally in component state
and then reinitializing on remount from defaults instead of verified backend state.

2. DEFAULT FALSE / DEFAULT OFF PAINT
Cards initialize as:
- off
- grey
- false
before async verification finishes.

This causes a false visual revert flash or persistent wrong state if hydration ordering is bad.

3. STALE RESPONSE OVERRIDE
A slower older request finishes after a newer one and overwrites verified current state.

Example:
- tab A loads
- verify call 1 starts
- user switches away and back
- verify call 2 starts
- call 2 returns applied=true
- then old call 1 returns stale/off/default and overwrites UI

4. MULTIPLE SOURCES OF TRUTH
Different parts of the app may be reading from different state sources:
- persisted frontend state
- local component state
- last action response
- background verification result
- backend checkStatus result

That must be collapsed to one canonical rendering source.

5. PENDING / APPLIED / VERIFIED STATES ARE MIXED TOGETHER
A card may be rendering from "pending visual state" or "last clicked option"
instead of the real verified applied state.

REQUIRED FIXES

1. SINGLE CANONICAL TWEAK VIEW MODEL
For every tweak, create one canonical frontend state model:
- status: 'unknown' | 'checking' | 'applied' | 'not_applied' | 'applying' | 'reverting' | 'error'
- verified: boolean
- lastVerifiedAt
- displayedValue
- actualValue
- pendingAction
- requestVersion

The card UI must render from this canonical model only.

No card should invent its own truth from local useState defaults.
