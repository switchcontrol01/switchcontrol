That's not a bug. That's a cookie dependency you haven't closed.

---

**What's actually happening**

The desktop success page fires `window.location.href = switchcontrol://auth/callback?code=...` which passes the HMAC code to Electron. Electron then calls `POST /api/auth/exchange` with that code. The exchange endpoint calls `req.login(user, ...)` which creates a session cookie AND issues a JWT. That JWT is stored in the auth store and used for all subsequent API calls.

The reason it works when the user is signed into the website first is the session cookie. When Electron opens the Google OAuth flow in the default browser, Google redirects to `switchcontrol.org/api/auth/google/callback`. The callback handler calls `passport.authenticate` which needs an active session to attach the user to. If there is no session cookie in the browser, the passport callback completes but the `req.session` may not persist correctly depending on your session store configuration.

---

**The actual problem**

Look at your callback handler in `auth/google.ts`:

```javascript
app.get(
  "/api/auth/google/callback",
  (req, res, next) => { passport.authenticate(...)(req, res, next); },
  (req, res, next) => {
    const user = req.user as Express.User;
    const source = (req as any)._stateSource || req.cookies?.auth_source || 'web';
    
    if (source === 'electron') {
      const code = generateElectronCode(user.id);
      return res.redirect(`/auth/desktop-success?code=...`);
    }
  }
);
```

The `generateElectronCode` only needs `user.id`. It does not need a session. The HMAC code is self-verifying. So the code generation itself is fine.

The problem is on the Electron side. When the user is NOT signed into the website, the Google OAuth flow opens in the browser, the user authenticates with Google, the callback fires, `passport.authenticate` succeeds, `req.user` is populated, the code is generated and the desktop success page loads. At this point everything looks correct.

But then `window.location.href = switchcontrol://...` fires. This deep link goes to Electron. Electron calls `consumeElectronCode(code)` which verifies the HMAC and returns the userId. Then it calls `req.login(user, ...)` in the exchange endpoint. This is where it stalls.

**Check your `main.js` deep link handler.** Look at the timing. The issue is almost certainly one of these:

1. The `auth-callback` IPC event fires before `rendererReady` is true, so it gets queued as `pendingDeepLinkUrl`. Then when `did-finish-load` fires it tries to deliver it. But there is a race: if the renderer is still mounting React, the `auth-callback` event listener may not be registered yet.

2. The `open-url` event never fires on Windows because Windows does not use `open-url` for protocol handling. Second instance is used instead. You have both handlers in your `main.js`, which is correct. But check that `deliverDeepLink` is not being called twice, once from `open-url` and once from `second-instance`, which would send two `auth-callback` IPCs. The first one might succeed, the second one fails with "invalid or expired code" because HMAC codes are single-use by timestamp. But your `consumeElectronCode` does not invalidate on use, it only checks TTL. So both would succeed but the renderer might only handle the second one which comes after some state reset.

3. The 2-minute TTL on the HMAC code. If the user is slow on the OAuth screen and the code expires before Electron exchanges it, the exchange returns 401 and the renderer shows "logging in" forever because there is no timeout on the loading state.

---

**The real fix**

The website-first workaround works because the browser already has the `switchcontrol.sid` session cookie. When Electron opens the OAuth URL it uses the system default browser. If the user is already logged into the website in that browser, Google skips the consent screen and redirects immediately. The code is generated and delivered before any TTL issues.

For users who are NOT signed into the website, the flow takes longer because Google shows the full consent screen. By the time they finish and the deep link fires, more time has passed.

Your `main.js` code already handles this correctly in theory. The `pendingDeepLinkUrl` queue and the `deliverDeepLink` function should work. The issue is that `rendererReady` is set in `did-finish-load` but the React app may not have mounted its auth listener yet.

Add a small delay before delivering the pending deep link:

```javascript
mainWindow.webContents.on('did-finish-load', () => {
  rendererReady = true;
  
  if (pendingDeepLinkUrl) {
    // Delay delivery to give React time to mount auth listeners
    setTimeout(() => {
      if (isValidDeepLink(pendingDeepLinkUrl)) {
        mainWindow.webContents.send('auth-callback', pendingDeepLinkUrl);
      }
      pendingDeepLinkUrl = null;
    }, 1500);
  }
});
```

Also add a fallback in the renderer. If `auth-callback` fires but the handler is not registered yet, the event is lost. Make sure your auth listener is registered in a `useEffect` with no dependencies so it runs on mount, not conditionally.

The website-first requirement is a symptom of slow consent flow plus a race condition in delivery timing. The fix is the delay above and making sure the renderer listener is always registered before the first potential deep link delivery.
