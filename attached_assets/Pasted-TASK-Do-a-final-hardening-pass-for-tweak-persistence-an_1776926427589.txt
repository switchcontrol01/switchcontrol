TASK

Do a final hardening pass for tweak persistence and state integrity across the entire app.

This is not a cosmetic pass.
This is a correctness + persistence + rehydration pass.

Users must be able to:
- apply a tweak
- revert a tweak
- switch tabs
- leave the tweak page
- close the app
- reopen the app
- still see the correct state
- and the actual Windows state must match the UI

The system must be hardened so tweak state never gets falsely reset, overwritten by stale data, or shown incorrectly after navigation or relaunch.

PROBLEM

There is still risk that tweak state is not fully trustworthy.

Users reported behavior like:
- apply tweak
- switch tabs
- go back
- tweak appears reset
- close app
- reopen app
- tweak state appears wrong
- network tweaks / other sections can desync too

Even if PowerShell multiplication is fixed, that does NOT prove tweak persistence is fixed.

We need to harden the full chain:
1. execution
2. verification
3. local persistence
4. backend persistence if used
5. rehydration on app launch
6. tab switching and remount behavior
7. race conditions between initial load, sync, and live verification

GOAL

Make tweak state bulletproof.

After this pass:
- tweak state survives tab changes
- tweak state survives route remounts
- tweak state survives app close and reopen
- UI reflects real system state, not stale guesses
- no background sync overwrites correct local state with defaults
- no mount effect can reset applied toggles
- no premium/auth/backend refresh can clobber local tweak state
- all tweak categories behave consistently:
  - standard tweaks
  - network tweaks
  - NIC tuning / NIC settings
  - power plans
  - app booster actions if stateful

HARD RULES

1. REAL STATE WINS
Displayed tweak state must come from verified current system state or trusted persisted state that is reconciled safely.
Never let a default false overwrite a previously known applied state during loading.

2. NO DESTRUCTIVE HYDRATION
On launch or page mount:
- do not initialize visible state to false and then later correct it
- do not blast empty/default state into stores before verification finishes
- do not let backend null/default responses replace local truth

3. WRITE AFTER SUCCESS ONLY
Only persist applied/reverted state after:
- command succeeded
- verification passed, or explicit verified state was returned

4. REHYDRATE ON LAUNCH
On app start, load persisted tweak state first as a provisional source, then reconcile with actual verification in a controlled way.
Never flash incorrect off states during this process.

5. TAB-SAFE
Switching tabs, remounting pages, reopening accordions, or re-entering routes must never reset tweak cards or toggles.

6. EXPLICIT LOADING STATE
If a tweak state is not yet known, show:
- loading / verifying / syncing
Do NOT show false/off unless it is actually known to be off.

7. STALE RESPONSE PROTECTION
Any async verify/sync/load response must be ignored if it belongs to an older request generation than the latest active page/session load.
