## What this screenshot is telling you

Two things stand out:

1. **"No memory layout data available"** — this is `si.memLayout()` either timing out or returning empty, which we've seen fail repeatedly in your logs (`phase=timeout source=memLayout limit=4000ms`).
2. **"EXPO/XMP: Unknown / Off"** and **"BIOS release date not available"** — both are inference results based on data that didn't come through.

This component is honest about not knowing things in *this* instance ("No memory layout data available," "Check Manufacturer Site") — but you're saying other times it shows full detail like "16x2 6200MHz." That's the actual bug: **the same component renders two structurally different outputs depending on whether the underlying WMI/PowerShell probes succeeded or timed out on that particular launch**, and there's no consistent fallback template — sometimes you get the rich format, sometimes you get the degraded "Unknown" format, and which one you see is essentially a coin flip based on whether `memLayout`/`baseboard`/`bios` WMI calls happened to respond in time that session.

## Why this connects directly to everything we just diagnosed

This is the *exact* same root cause as the startup lag and audio glitch — `SysIntelligence`'s deep collection probes (`memLayout`, `baseboard`, `bios`, etc.) are timing out inconsistently, probe by probe, launch by launch. Sometimes `memLayout` happens to come back in time, sometimes it doesn't. BIOS Advisor is just the first place where that inconsistency became *visibly* obvious to you, because it's directly displaying the raw success/failure of those same probes as different UI states.

This also lines up with something we already decided: **defer hardware scanning until the user opens the relevant page, rather than racing fragile WMI calls against tight timeouts at startup.** BIOS Advisor inheriting stale/partial/mixed data from a startup scan that already half-failed is a direct consequence of the eager-loading pattern we discussed fixing for Driver Intelligence — this is proof it's already actively causing visible bugs elsewhere in the app, today.

## The actual fix, concretely

1. **BIOS Advisor should trigger its own fresh, dedicated probe when the page opens** — not rely on whatever partial/timed-out data `SysIntelligence`'s startup sweep happened to gather. If the user is actively looking at this page, it's worth taking the extra 3-4 seconds to get a real answer rather than showing whatever leftover state exists from launch.

2. **Pick one rendering mode and apply it consistently, not two different layouts depending on data luck.** Right now it sounds like there are effectively two UI templates — "rich, fully populated" and "Unknown/Off, Check Manufacturer Site" — and which one renders is accidental based on timing. The fix isn't "make the data load faster" (though that helps) — it's "the component should have one consistent loading→success→partial-failure state machine," so even when data is incomplete, it degrades the same way every time, rather than flipping between two completely different visual layouts.

3. **Cache successful probe results and only re-show "Unknown" for fields that are genuinely still missing**, not the whole card. If `memLayout` failed but `baseboard` succeeded, show CPU/BIOS info normally and only the memory section as "Unknown" — rather than the whole hardware profile rendering differently based on which single probe happened to be the slow one that session.
