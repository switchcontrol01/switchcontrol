This confirms and adds to the picture. Here's the schema-level analysis.

## Critical issue #1: Missing indexes on every foreign-key-style column

Not a single explicit index exists anywhere in this schema beyond primary keys. Specifically:

- `appliedTweaks.settingsId` — no index. Every lookup of "tweaks for this user" does a full table scan once this table grows past a few thousand rows.
- `historyEntries.settingsId` — same problem, and this table grows *unboundedly* per user (every action logs a new row). At 10k users generating history entries regularly, this becomes your slowest table within weeks, not months.
- `aiScans.settingsId` — same pattern.
- `networkTweakLog.userId` and `networkTweakLog.tweakId` — no index, and this is an append-only log table too.

Drizzle relations (`relations()`) define the *application-level* join semantics for the query builder, but they do **not** create a database index. Postgres will not automatically index a foreign-key-shaped column — you have to add it explicitly. Right now, every one of these "get all X for this user" queries — which is probably the single most common query pattern in your whole app — is doing a sequential scan.

At 10k users this is the difference between sub-millisecond queries and queries that get progressively slower as `historyEntries` and `networkTweakLog` grow, since both are pure write-heavy, never-pruned tables.

**Fix:** add explicit indexes:
```typescript
export const appliedTweaks = pgTable("applied_tweaks", {
  ...
}, (t) => ({
  settingsIdIdx: index("applied_tweaks_settings_id_idx").on(t.settingsId),
}));
```
Same pattern for `historyEntries.settingsId`, `aiScans.settingsId`, `networkTweakLog.userId`.

## Critical issue #2: `userSettings.userId` is `unique()` but not the primary key, and everything else joins through `settingsId` instead of `userId` directly

This is an architectural smell more than a hard bug, but it matters at scale. The pattern here is: `userId` → look up `userSettings.id` → use that UUID as the foreign key everywhere else (`settingsId`). That's an extra join/lookup on basically every query in your app. It works fine at low volume, but it means every single feature touch requires resolving `userId → settingsId` first, then querying the child table. You're paying a double-lookup tax on every request, on every table.

At 10k users this isn't fatal by itself (especially once indexed), but combined with the missing indexes above, this compounds — you'd be doing two unindexed-then-indexed lookups instead of one.

## Critical issue #3: unbounded history-style tables with no retention strategy

`historyEntries`, `aiScans`, and `networkTweakLog` are all append-only with no TTL, no archiving, no pagination-friendly design visible. At 10k active users logging actions regularly, these tables could realistically hit tens of millions of rows within a year. Without indexes (see above) and without any retention/cleanup job, query performance degrades continuously over time even after you fix the indexing — because the tables just keep growing forever.

You need either: a scheduled job that prunes/archives old rows past N days, or a hard cap per user (e.g. "keep only the last 500 history entries"), or move to a time-series-friendly storage if you want full retention.

## Smaller things worth flagging

- `networkTweakLog.id` is `serial` (32-bit integer) — fine up to ~2 billion rows, not a near-term concern, but worth knowing it's there if this table grows as fast as I expect.
- `userSettings.usedRamGb` defaulting to `9.5` and `email` defaulting to `"user@example.com"` look like leftover placeholder/seed defaults rather than real production defaults — not a scaling issue, but worth cleaning up before 10k real users start seeing those as fallback values if a write ever omits them.
- No `onDelete` cascade behavior specified anywhere in the relations — if a user is ever deleted, you'd need to manually clean up `appliedTweaks`, `historyEntries`, `aiScans`, `networkTweakState`, `networkTweakLog` rows or they become orphaned forever, slowly bloating those same already-unindexed tables.

## Verdict so far

Combined with the connection pool issue from before, **this schema and pool config would likely fail or badly degrade well before 10k concurrent users** — probably starting to show real pain in the low thousands of *active* users, because:

1. Pool max of 10 chokes first under concurrent load.
2. Every history/log/scan table query is doing full scans without indexes.
3. Those same tables grow forever with no pruning.

None of this requires a rewrite — it's all additive fixes (indexes + pool sizing + a cleanup job), not architectural changes. But it does need to happen before you scale, not after you start seeing timeouts in production.
